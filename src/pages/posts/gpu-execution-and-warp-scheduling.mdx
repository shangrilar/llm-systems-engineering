지난 글에서는 원소별 연산, reduction, 행렬 곱에서 어떤 결과를 독립적으로 계산할 수 있는지 살펴봤습니다. 나눌 수 있는 계산이 많다면 GPU는 이를 어떻게 맡아서 실행할까요? 이번에는 **계산을 작업 묶음으로 구성하고, SM에 배정한 뒤, 실행할 수 있는 작업을 선택하는 과정**을 알아보겠습니다.

여기서는 NVIDIA GPU를 기준으로 설명합니다. 벡터 덧셈을 작은 작업들로 나누는 것에서 시작해, 데이터를 기다리는 동안 다른 계산을 진행하는 방식까지 연결하겠습니다.

## 많은 계산을 작업 묶음으로 구성하기

두 벡터의 같은 위치에 있는 값을 더해 출력 1,024개를 만든다고 생각해 보겠습니다. GPU가 수행할 일은 입력을 읽고, 더하고, 결과를 저장하는 것입니다. 이런 처리 절차를 GPU에서 실행할 함수로 작성한 것을 **커널**(kernel)이라고 부릅니다. 여기서는 벡터 덧셈 커널을 한 번 실행하는 과정을 살펴보겠습니다.

지난 글에서 본 것처럼 각 출력은 다른 위치의 결과를 기다리지 않고 계산할 수 있습니다. 출력 하나를 만드는 일을 개별 실행 흐름 하나에 맡겨 보겠습니다. 이 **개별 실행 흐름을 쓰레드**(thread)라고 부릅니다. 각 thread는 자신이 담당하는 위치의 입력 두 값을 읽고, 두 값을 더한 뒤 결과를 저장합니다. 모든 thread가 같은 커널을 실행하면서 각자 맡은 데이터를 처리하는 것입니다.

이 thread들을 함께 관리할 묶음이 필요합니다. **여러 thread를 묶어 SM에 함께 배정하는 작업 단위가 블록**(block)입니다. 같은 block의 thread들은 데이터를 공유하며 협력할 수도 있습니다. 여기서는 thread 128개를 block 하나로 묶겠습니다. Thread 하나가 출력 하나를 담당하므로 block 하나는 출력 128개를 계산합니다.

출력 1,024개를 처리하려면 이런 block이 여덟 개 필요합니다. **한 번의 커널 실행에 속한 block 전체를 그리드**(grid)라고 부릅니다. 따라서 이번 실행은 grid 하나에 block 여덟 개가 있고, 각 block에 thread 128개가 있는 구성입니다. [CUDA의 작업 구성](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html)을 그림 1에서 함께 보겠습니다.

[![Grid 안에 block A부터 H까지 여덟 개가 있으며, 각 block에 thread 128개라고 표시되어 있습니다. 작은 칸은 thread의 일부를 보여줍니다. Thread 하나를 확대하면 입력 1과 10을 읽고, 더한 뒤, 결과 11을 저장합니다.](/images/gpu-execution-and-warp-scheduling/01-work-groups.png)](/images/gpu-execution-and-warp-scheduling/01-work-groups.png)

그림의 왼쪽에서 block A는 첫 128개 출력을, block B는 그다음 128개 출력을 담당합니다. 오른쪽은 그중 thread 하나가 맡은 일을 확대한 것입니다. **커널이 수행할 처리 절차를 정한다면, grid와 block은 그 절차를 실행할 많은 thread를 묶는 구조**입니다.

이런 작업 구성은 커널을 구현하고 실행하는 쪽에서 정합니다. 예를 들어 thread당 출력 하나, block당 thread 128개라는 구성을 유지하면서 입력 길이가 2,048로 늘어나면 block은 16개가 됩니다. **작업을 어떤 단위로 묶을지 정하는 것과, 그 묶음을 실제 GPU에서 실행하는 것은 구분할 수 있습니다.** 이제 이렇게 구성한 block이 어디에서 실행되는지 살펴보겠습니다.

## Block: SM에 배정하고 자원을 확보하기

앞서 GPU 구조를 설명할 때, GPU 안에는 여러 SM이 있고 각 SM에 연산 장치와 register, L1 캐시·shared memory가 있다고 했습니다. **GPU는 block을 SM에 배정하며, block 하나의 thread들은 같은 SM에서 실행됩니다.** 작업이 SM에 배정되어 실행에 필요한 자원을 차지한 상태를 **상주**(resident)한다고 표현합니다.

[![SM 배정을 기다리는 block E부터 H가 위에 있고, SM 1에는 A와 B, SM 2에는 C와 D가 상주합니다. 각 block에는 thread별 register와 block 내에서 공유하는 shared memory가 표시되어 있으며, 각 SM의 L1 캐시는 여러 block이 활용합니다.](/images/gpu-execution-and-warp-scheduling/02-blocks-on-sms.png)](/images/gpu-execution-and-warp-scheduling/02-blocks-on-sms.png)

그림 2에서 block A와 B는 SM 1에, C와 D는 SM 2에 배정되어 있습니다. 한 SM에는 block 하나만 들어가는 것이 아니라, 자원이 허용하는 만큼 여러 block이 상주할 수 있습니다.

상주하는 작업은 SM의 저장 공간을 사용합니다. **Register에는 각 thread가 사용하는 값과 중간 결과를 보관합니다.** 그림 1의 덧셈을 떠올리면, thread마다 자신이 읽어 온 입력과 계산 결과가 필요합니다. 물리적인 register 자원은 SM 안에 있지만, 그 안에 보관하는 값은 thread별로 구분됩니다.

**Shared memory는 같은 block의 thread들이 데이터를 공유하며 협력할 때 사용할 수 있는 공간**입니다. 예를 들어 여러 thread가 부분합을 만든 뒤 함께 합칠 때, 중간 값을 이 공간에 놓고 사용할 수 있습니다. 필요한 값이 준비된 뒤 다음 계산으로 넘어가도록 실행 시점을 맞추는 것을 동기화라고 합니다. 부분합을 함께 합치는 계산에서도, 다른 thread가 만든 값이 준비된 뒤 읽도록 동기화할 수 있습니다.

L1 캐시는 같은 SM에 있는 여러 block의 메모리 접근에 활용됩니다. Shared memory와 L1 캐시는 앞서 살펴본 통합 공간을 나누어 사용하지만, thread들이 데이터를 명시적으로 공유하는 공간과 하드웨어가 관리하는 캐시라는 역할의 차이가 있습니다.

SM의 자원은 한정되어 있습니다. 먼저 배정된 작업들이 register나 shared memory를 많이 사용한다면 추가 block을 받아들일 공간이 부족할 수 있습니다. 그림 위쪽의 E부터 H는 아직 배정되지 않은 작업입니다. 실행 중인 block이 완료되어 자원이 반환되면 기다리던 block을 추가로 배정할 수 있습니다. 따라서 **grid에 속한 block이 많다고 해서 모두 같은 순간에 SM에 상주하는 것은 아닙니다.** [상주 가능한 수](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#execution-configuration-optimizations)는 자원 사용량뿐 아니라 하드웨어의 block·thread 수 한도에도 영향을 받습니다.

## Warp: 32개 thread의 명령을 함께 실행하기

Block이 SM에 배정되었다면 그 안의 thread들은 어떻게 실행될까요? NVIDIA GPU는 **같은 block의 thread들을 32개씩 묶은 warp를 단위로 명령을 스케줄링합니다.** 그림 3에서는 thread 128개인 block 하나가 네 개의 warp로 나뉩니다.

[![Thread 128개로 이루어진 block 하나에 warp 네 개가 있고, 각 warp에는 thread 32개가 있습니다. Warp 하나의 thread 네 개를 확대하면 같은 덧셈 명령으로 각각 1+10, 2+20, 3+30, 4+40을 계산합니다.](/images/gpu-execution-and-warp-scheduling/03-warps-and-threads.png)](/images/gpu-execution-and-warp-scheduling/03-warps-and-threads.png)

Warp 0 안의 thread 네 개를 확대해 보겠습니다. Thread 0은 `1 + 10`을, thread 1은 `2 + 20`을 계산합니다. 나머지 두 thread도 각자 다른 입력을 더합니다. **실행하는 명령은 덧셈으로 같지만, 그 명령에 사용하는 값과 결과는 thread마다 다릅니다.**

GPU는 이런 방식으로 여러 thread에 공통 명령을 적용해 계산합니다. 이를 **[SIMT](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#simt-execution-model)**(Single Instruction, Multiple Threads)라고 부릅니다. 그림처럼 모든 thread가 같은 덧셈에 참여할 수도 있고, 조건문에 따라 한 명령에 일부 thread만 참여할 수도 있습니다.

**Thread는 계산을 수행하는 실행 흐름이고, CUDA Core는 명령을 처리하는 물리적인 연산 장치**입니다. Thread마다 전용 CUDA Core를 하나씩 차지하는 관계는 아닙니다.

여기까지 연결하면, block은 SM에 배정되는 단위이고 warp는 SM 안에서 명령을 스케줄링하는 단위입니다. 그렇다면 SM에 여러 warp가 상주할 때, 다음에는 어느 warp의 명령을 실행해야 할까요?

## Warp 스케줄링: 준비된 다음 명령 선택하기

SM 안의 **warp scheduler는 자신이 담당하는 warp들 가운데 다음 명령을 실행할 수 있는 warp를 선택합니다.** 선택한 명령을 실행 장치로 보내는 것을 **명령 발행**(issue)이라고 합니다. 발행한 명령의 결과는 실행을 거쳐 나중에 준비됩니다.

SM에는 여러 warp scheduler가 있습니다. 그림 4는 그중 한 스케줄러가 담당하는 warp 네 개와 다음 명령을 선택하는 모습을 보여줍니다.

[![한 스케줄러에 상주하는 warp A와 C는 각각 메모리 결과와 동기화를 기다립니다. B와 D는 실행 가능한 상태이고, 스케줄러는 이번에 B를 선택해 다음 명령을 발행합니다. 상주 4개, 실행 가능 2개, 이번에 선택 1개입니다.](/images/gpu-execution-and-warp-scheduling/04-ready-warps.png)](/images/gpu-execution-and-warp-scheduling/04-ready-warps.png)

Warp A는 메모리에서 읽어 올 값을 기다리고 있습니다. 다음 덧셈에 그 값이 필요하다면 아직 덧셈을 실행할 수 없습니다. Warp C는 동기화 지점에서 다른 thread들의 작업이 준비되기를 기다립니다. 반면 B와 D는 다음 명령을 진행할 준비가 되어 있습니다.

이 순간에는 **상주하는 warp가 네 개이지만, 실행 가능한 후보는 두 개**입니다. 스케줄러는 그중 B를 선택해 다음 명령을 발행합니다. D도 준비되어 있지만 이번에는 선택되지 않았습니다. A·C처럼 진행 조건을 기다리는 상태와 D처럼 준비되었으나 선택되지 않은 상태는 다릅니다. [실행 가능한 후보](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#sections-and-rules)가 되려면 필요한 입력과 앞선 계산 결과뿐 아니라 명령을 처리할 실행 자원도 준비되어야 합니다.

**선택하는 대상은 warp가 수행할 다음 명령입니다.** B의 작업 전체가 끝날 때까지 계속 B만 실행해야 하는 것은 아닙니다. B의 명령을 발행한 뒤에는, 그다음 시점에 준비된 후보 가운데 D를 선택할 수도 있습니다. 아직 진행 중인 명령이 있더라도 다른 명령을 발행할 수 있는지는 각 명령의 의존성과 실행 자원에 달려 있습니다.

**기다리는 warp의 register 값과 실행 상태도 SM 안에 유지됩니다.** 스케줄러는 이렇게 상태가 보관된 warp들 중에서 다음 명령을 실행할 대상을 고릅니다. 대기하던 warp의 진행 조건이 충족되면 다시 선택 후보가 됩니다.

## 지연 숨기기: 기다리는 동안 다른 작업 진행하기

이제 앞서 설명한 메모리 접근 지연과 연결해 보겠습니다. 메모리에 값을 요청한 뒤 실제로 사용할 수 있을 때까지는 시간이 걸립니다. 그 값을 기다리는 계산은 멈춰 있어도, **준비된 다른 warp의 계산은 진행할 수 있습니다.**

[![Warp A가 읽기를 요청하고 입력을 기다리는 동안 다른 warp가 준비되어 있으면 B와 D의 명령을 발행합니다. 다른 warp도 모두 기다리는 경우에는 같은 대기 시간 동안 명령 발행이 비어 있습니다. A의 입력이 준비되면 덧셈을 진행할 수 있습니다.](/images/gpu-execution-and-warp-scheduling/05-latency-hiding.png)](/images/gpu-execution-and-warp-scheduling/05-latency-hiding.png)

그림 5의 위쪽에서 A는 메모리 읽기를 요청합니다. 이어지는 덧셈에는 그 입력이 필요하므로 데이터가 도착할 때까지 기다립니다. 그동안 스케줄러는 준비된 B와 D의 명령을 발행합니다. 이후 A의 입력이 준비되면 A의 덧셈도 선택해 실행할 수 있습니다.

아래쪽에서는 A뿐 아니라 다른 warp들도 모두 기다리고 있습니다. 이 경우 스케줄러에 실행 가능한 후보가 없으므로 새로운 명령을 발행하지 못합니다. 앞서 발행한 메모리 요청이나 연산은 계속 진행될 수 있지만, 이 스케줄러가 실행 장치에 추가로 맡길 명령은 없는 상태입니다.

두 경우에서 A의 데이터 대기 시간은 같다고 가정했습니다. 차이는 **그 시간 동안 다른 작업을 진행했는지**입니다. 이처럼 다른 작업의 실행으로 대기 시간의 영향을 줄이는 것을 **지연 숨기기**(latency hiding)라고 합니다.

상주하는 warp가 많으면 다른 작업을 선택할 여지가 생깁니다. 하지만 그 warp들이 모두 같은 시점에 기다리고 있다면 실행할 후보가 없습니다. 따라서 GPU의 실행을 볼 때는 **얼마나 많은 작업을 배정했는지와, 그중 지금 진행할 수 있는 작업이 얼마나 있는지를 함께 생각해야 합니다.** 이것이 많은 thread를 묶어 관리하고 준비된 warp의 명령을 선택하는 방식이 중요한 이유입니다.

다음 글에서는 이 실행 구조를 바탕으로 작업을 어떻게 나누면 GPU를 더 효율적으로 사용할 수 있는지 살펴보겠습니다. 원소별 연산과 행렬 곱에서 각 작업이 맡을 계산의 양, 필요한 데이터의 이동, 가져온 데이터의 재사용을 연결하겠습니다.
