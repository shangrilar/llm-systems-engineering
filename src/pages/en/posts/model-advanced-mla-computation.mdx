[The previous article](/en/posts/model-advanced-mla-storage/) explained how MLA caches a shared latent vector and a positional key instead of storing every head's keys and values. But if every new token required expanding all past K and V vectors again, reconstructing them would still take computation.

MLA can **move the computation that expands K and V while preserving the result.** It moves the key projection to the current query and applies the value projection after combining information across positions. This reduces repeated projections at cached positions and lets attention read the compact latent representation directly.

We will first see how the current token produces its query and how content and positional information contribute to attention scores. Then we will reorder the key and value computations to see which operations disappear and which remain. We will follow the processing of the current token in one layer during token-by-token generation.

## Building queries for the current token

As before, let the current position be <math aria-label="p3"><mrow><msub><mi>p</mi><mrow><mn>3</mn></mrow></msub></mrow></math> and the input dimension be 8. The cache contains latent vectors and positional keys for four positions, <math aria-label="p0"><mrow><msub><mi>p</mi><mrow><mn>0</mn></mrow></msub></mrow></math> through the current <math aria-label="p3"><mrow><msub><mi>p</mi><mrow><mn>3</mn></mrow></msub></mrow></math>. The KV latent dimension is 3, each head's content key and value dimensions are 2, and the positional dimension is also 2. These small dimensions are illustrative.

We now build the query that will read the cache. Each block at the top of Figure 1 represents an entire input vector at one position. The lower part shows two query heads produced from <math aria-label="p3"><mrow><msub><mi>p</mi><mrow><mn>3</mn></mrow></msub></mrow></math>.

<a href="/images/model-advanced-mla-computation/en/00-query-path.png?v=ed7b8a65d29f" id="figure-1"><picture><source width="720" height="2312" media="(max-width: 600px)" srcSet="/images/model-advanced-mla-computation/en/00-query-path-mobile.png?v=12d61315b55b" /><img width="2400" height="2366" src="/images/model-advanced-mla-computation/en/00-query-path.png?v=ed7b8a65d29f" alt="The current p3 input vector (1×8) is multiplied by Wᴰ^Q (8×3) to produce a query latent c^Q (1×3). Each head projects it through U^Q (3×2) for the content query and W^Qᴿ (3×2), followed by RoPE(p3), for the position query. Both parts are 1×2 and head-specific. The position key remains shared across heads, as in Article 2." loading="lazy" /></picture></a>

Applying the 8×3 projection <math aria-label="W^DQ"><mrow><msup><mi>W</mi><mi mathvariant="normal">DQ</mi></msup></mrow></math> to the current input <math aria-label="x3"><mrow><msub><mi>x</mi><mrow><mn>3</mn></mrow></msub></mrow></math> produces the query latent vector <math aria-label="c_3^Q"><mrow><msubsup><mi>c</mi><mrow><mn>3</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math>. This and the cached KV latent vector <math aria-label="c3"><mrow><msub><mi>c</mi><mrow><mn>3</mn></mrow></msub></mrow></math> from the previous article are **representations produced by different weights**. Both have three components in this example, but their dimensions do not have to match in an actual model.

Each head produces two kinds of query from <math aria-label="c_3^Q"><mrow><msubsup><mi>c</mi><mrow><mn>3</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math>. For head 1, the 3×2 projection <math aria-label="U_1^Q"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math> produces a two-component **content query**. <math aria-label="W_1^QR"><mrow><msubsup><mi>W</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">QR</mi></msubsup></mrow></math> is also a 3×2 projection, but its output undergoes the RoPE rotation for the current position to produce a **positional query**. Head 2 uses its own weights, so both query parts differ by head. This follows [DeepSeek-V2's low-rank query projection and decoupled RoPE construction](https://arxiv.org/html/2405.04434v5#S2.SS1.SSS3).

From here on, we will show both position and head indices. <math aria-label="q_(3,1)^C"><mrow><msubsup><mi>q</mi><mrow><mn>3</mn><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">C</mi></msubsup></mrow></math> is the **content query for position 3, head 1**, and <math aria-label="q_(3,1)^R"><mrow><msubsup><mi>q</mi><mrow><mn>3</mn><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">R</mi></msubsup></mrow></math> is the positional query for the same position and head. Superscripts C and R distinguish the content and RoPE paths. Figure 1 omits the position subscript because the current position is fixed; Figure 2 onward includes both indices.

Positional queries are per-head, whereas all heads share the positional key at a given cached position. Thus, **different queries can produce different positional scores even when they read the same positional key.** Queries are used to compute scores now; past queries do not need to accumulate in the KV cache.

The figure focuses on projections and positional rotation. It omits steps such as normalization of latent vectors. [DeepSeek-V2's model configuration](https://arxiv.org/html/2405.04434v5#S3.SS1.SSS2) also includes RMSNorm after latent vectors. When we combine operations below, we mean **consecutive linear projections after normalization**.

## Adding content and positional scores

Let <math aria-label="j"><mrow><mi>j</mi></mrow></math> denote the position being read from the cache. With current position 3, <math aria-label="j"><mrow><mi>j</mi></mrow></math> can be 0, 1, 2, or 3. To read position <math aria-label="j"><mrow><mi>j</mi></mrow></math>, head 1 needs its content key, positional key, and value.

The left side of Figure 2 shows the K and V construction from the previous article; the right side shows how the current query produces a score. We will start by expanding K and V before computing attention.

<a href="/images/model-advanced-mla-computation/en/01-expanded-reference.png?v=e9dac7030f30" id="figure-2"><picture><source width="720" height="2678" media="(max-width: 600px)" srcSet="/images/model-advanced-mla-computation/en/01-expanded-reference-mobile.png?v=12e5e1ede018" /><img width="2400" height="2240" src="/images/model-advanced-mla-computation/en/01-expanded-reference.png?v=e9dac7030f30" alt="Left: latent cⱼ (1×3) is projected by head 1 matrices Uᴷ₁ and Uⱽ₁ (3×2) into content key and value vectors (1×2). Position key kⱼᴿ (1×2) is shared across heads. Right: add the content and position query-key dot products, scale and softmax across positions, then combine values with the resulting weights." loading="lazy" /></picture></a>

The latent vector <math aria-label="c_j"><mrow><msub><mi>c</mi><mrow><mi>j</mi></mrow></msub></mrow></math> at position <math aria-label="j"><mrow><mi>j</mi></mrow></math> has shape 1×3. Multiplying it by head 1's <math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> produces content key <math aria-label="k_(j,1)^C"><mrow><msubsup><mi>k</mi><mrow><mi>j</mi><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">C</mi></msubsup></mrow></math>; multiplying it by <math aria-label="U_1^V"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math> produces value <math aria-label="v_(j,1)"><mrow><msub><mi>v</mi><mrow><mi>j</mi><mo>,</mo><mn>1</mn></mrow></msub></mrow></math>. Both projections have shape 3×2, and each result has shape 1×2. The separately cached positional key <math aria-label="k_j^R"><mrow><msubsup><mi>k</mi><mrow><mi>j</mi></mrow><mi mathvariant="normal">R</mi></msubsup></mrow></math> is also 1×2, but has no head index because it is shared across heads.

The current query and cached key take **dot products between matching parts**: content query with content key, positional query with positional key. Each dot product gives one number. Adding them produces score <math aria-label="s_j"><mrow><msub><mi>s</mi><mrow><mi>j</mi></mrow></msub></mrow></math> for position <math aria-label="j"><mrow><mi>j</mi></mrow></math>.

<math display="block" aria-label="s_j = q^C_(3,1) dot k^C_(j,1) + q^R_(3,1) dot k^R_j"><mrow><msub><mi>s</mi><mrow><mi>j</mi></mrow></msub><mo>=</mo><msubsup><mi>q</mi><mrow><mn>3</mn><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">C</mi></msubsup><mo>·</mo><msubsup><mi>k</mi><mrow><mi>j</mi><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">C</mi></msubsup><mo>+</mo><msubsup><mi>q</mi><mrow><mn>3</mn><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">R</mi></msubsup><mo>·</mo><msubsup><mi>k</mi><mrow><mi>j</mi></mrow><mi mathvariant="normal">R</mi></msubsup></mrow></math>

The dot symbol denotes a vector dot product. Concatenating the content and positional parts, as in the previous article, and taking one dot product gives the same result. For example, content query [2, 1] and content key [1, 2] give 4, while already-rotated positional query [1, 0] and positional key [0.6, 0.8] give 0.6. The total is 4.6. Content and positional parts are not cross-multiplied.

After computing scores for all four positions, we apply [scaling and softmax](/en/posts/core-attention/). The original query/key dimension here is content 2 plus positional 2, or 4, so the basic scaling divisor is √(2+2) = 2. Dividing each score by 2 and applying softmax **across all four positions** yields attention weights <math aria-label="a_j"><mrow><msub><mi>a</mi><mrow><mi>j</mi></mrow></msub></mrow></math>. We do not apply softmax independently to a single score at each position.

Combining <math aria-label="v_(j,1)"><mrow><msub><mi>v</mi><mrow><mi>j</mi><mo>,</mo><mn>1</mn></mrow></msub></mrow></math> with these weights produces head 1's output <math aria-label="o_(3,1)"><mrow><msub><mi>o</mi><mrow><mn>3</mn><mo>,</mo><mn>1</mn></mrow></msub></mrow></math>. Positional information influences how much weight each position receives, but **the positional key is not appended to the value for the weighted sum**. The current token can attend through its own position; when computing multiple tokens together, a causal mask must prevent them from reading future positions.

This is the basic attention computation represented by MLA. The next two sections preserve its result while eliminating the step that expands all per-head K and V vectors.

## Moving the key projection to the query

Path A in Figure 3 transforms the latent vector at each of the four positions into a content key. Head 1 uses the same projection <math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> at every position. We can exploit the fact that **the same linear transformation is repeated**.

<a href="/images/model-advanced-mla-computation/en/02-key-absorption.png?v=dd95362c6050" id="figure-3"><picture><source width="720" height="3056" media="(max-width: 600px)" srcSet="/images/model-advanced-mla-computation/en/02-key-absorption-mobile.png?v=941fa421ef28" /><img width="2400" height="2544" src="/images/model-advanced-mla-computation/en/02-key-absorption.png?v=dd95362c6050" alt="For head 1 and positions p0 through p3, the left path projects four cached latents into content keys, then dots them with the current query. The right path projects the query once from 1×2 to 1×3, then dots it directly with the four cached latents. Both produce the same four content scores." loading="lazy" /></picture></a>

Write the current content query <math aria-label="q_(3,1)^C"><mrow><msubsup><mi>q</mi><mrow><mn>3</mn><mo>,</mo><mn>1</mn></mrow><mi mathvariant="normal">C</mi></msubsup></mrow></math> as <math aria-label="q"><mrow><mi>q</mi></mrow></math> for brevity. The content score at position <math aria-label="j"><mrow><mi>j</mi></mrow></math> is the dot product of <math aria-label="q"><mrow><mi>q</mi></mrow></math> and <math aria-label="c_j"><mrow><msub><mi>c</mi><mrow><mi>j</mi></mrow></msub></mrow></math><math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math>. With row vectors, we transpose the key side to form a dot product. The superscript T means exchanging rows and columns.

<math display="block" aria-label="q (c_j U^K_1)^T = (q (U^K_1)^T) c_j^T"><mrow><mi>q</mi><msup><mrow><mo>(</mo><msub><mi>c</mi><mrow><mi>j</mi></mrow></msub><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup><mo>)</mo></mrow><mi mathvariant="normal">T</mi></msup><mo>=</mo><mrow><mo>(</mo><mi>q</mi><msup><mrow><mo>(</mo><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup><mo>)</mo></mrow><mi mathvariant="normal">T</mi></msup><mo>)</mo></mrow><msup><msub><mi>c</mi><mrow><mi>j</mi></mrow></msub><mi mathvariant="normal">T</mi></msup></mrow></math>

Compare what each side computes first. The left side multiplies the latent vector by <math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> to produce a key. The right side **first multiplies the current query by the transposed projection**. Call the result <math aria-label="q tilde"><mrow><mover><mi>q</mi><mo>˜</mo></mover></mrow></math>; its shape is (1×2)×(2×3) = 1×3. We can now take its dot product directly with the 1×3 latent vector <math aria-label="c_j"><mrow><msub><mi>c</mi><mrow><mi>j</mi></mrow></msub></mrow></math>. This does not arbitrarily swap the order of factors. Transpose properties and the associativity of matrix multiplication let us regroup the computation.

Check this with small numbers. Suppose <math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> selects the first two components of <math aria-label="c3"><mrow><msub><mi>c</mi><mrow><mn>3</mn></mrow></msub></mrow></math> = [1, 2, 3], as in the previous article. The content key is [1, 2], whose dot product with <math aria-label="q"><mrow><mi>q</mi></mrow></math> = [2, 1] is 2×1 + 1×2 = 4. Applying the transpose of that same projection to <math aria-label="q"><mrow><mi>q</mi></mrow></math> instead gives <math aria-label="q tilde"><mrow><mover><mi>q</mi><mo>˜</mo></mover></mrow></math> = [2, 1, 0]. Its dot product with <math aria-label="c3"><mrow><msub><mi>c</mi><mrow><mn>3</mn></mrow></msub></mrow></math> is also 2×1 + 1×2 + 0×3 = 4.

The same relation holds at other positions. Let <math aria-label="C"><mrow><mi>C</mi></mrow></math> be the 4×3 matrix whose rows are the four latent vectors. Path A constructs four keys with <math aria-label="C"><mrow><mi>C</mi></mrow></math><math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> and then computes scores. Path B constructs <math aria-label="q tilde"><mrow><mover><mi>q</mi><mo>˜</mo></mover></mrow></math> **once for the current head**, then computes directly with the four rows of <math aria-label="C"><mrow><mi>C</mi></mrow></math>.

<math display="block" aria-label="q (C U^K_1)^T = q tilde C^T"><mrow><mi>q</mi><msup><mrow><mo>(</mo><mi>C</mi><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup><mo>)</mo></mrow><mi mathvariant="normal">T</mi></msup><mo>=</mo><mover><mi>q</mi><mo>˜</mo></mover><msup><mi>C</mi><mi mathvariant="normal">T</mi></msup></mrow></math>

Both results contain four content scores, with shape 1×4. Even as the cache grows, the current query's transformation is not repeated for each position. Reading positions and computing scores with the transformed query still remain. The four projection blocks illustrate vector-level computations; they do not imply four separate GPU kernel launches.

### Why the RoPE path is separate

We can now explain why the previous article cached positional keys separately. If we applied position <math aria-label="j"><mrow><mi>j</mi></mrow></math>'s RoPE rotation to each expanded content key, the key projection would be followed by **a rotation that varies by position**. Moving this to the query side would make the query transformation depend on the position <math aria-label="j"><mrow><mi>j</mi></mrow></math> being read. We could no longer use one transformed query across all positions in the same way.

MLA applies RoPE to separate query/key parts, allowing the content path to keep the reordering in Figure 3. Positional scores are still computed separately and added as in Figure 2. [DeepSeek-V2's decoupled RoPE explanation](https://arxiv.org/html/2405.04434v5#S2.SS1.SSS3)

This does not mean latent vectors can never contain position-related information. The key question is **which path receives explicit position-dependent rotation**. Nor should we change the scaling divisor to √(3+2) because the content dot product now uses a three-dimensional latent space. It computes the same scores, so we retain √(2+2).

## Moving the value projection after the weighted sum

Once we add the positional scores and apply softmax, we know how much to use each position. Collect these attention weights into row vector <math aria-label="a"><mrow><mi>a</mi></mrow></math>, of shape 1×4. These weights are input-dependent proportions, distinct from the learned projection matrices.

Both paths in Figure 4 start with **the same cache and the same attention weights**. A constructs a value at each position before taking their weighted sum. B takes a weighted sum of latent vectors first.

<a href="/images/model-advanced-mla-computation/en/03-value-absorption.png?v=4f572f4553c5" id="figure-4"><picture><source width="720" height="3106" media="(max-width: 600px)" srcSet="/images/model-advanced-mla-computation/en/03-value-absorption-mobile.png?v=d160c8c482d9" /><img width="2400" height="2584" src="/images/model-advanced-mla-computation/en/03-value-absorption.png?v=4f572f4553c5" alt="Left: project each of four cached latents from 1×3 into values of size 1×2, then take their weighted sum. Right: use the same weights to combine latents into z (1×3), then apply the same Uⱽ₁ once. Both yield the same o₃,₁ (1×2)." loading="lazy" /></picture></a>

A applies the 3×2 projection <math aria-label="U_1^V"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math> to the 4×3 cache <math aria-label="C"><mrow><mi>C</mi></mrow></math>, producing a 4×2 value matrix. Multiplying by <math aria-label="a"><mrow><mi>a</mi></mrow></math> combines the four values into a 1×2 output. B first multiplies <math aria-label="a"><mrow><mi>a</mi></mrow></math> by <math aria-label="C"><mrow><mi>C</mi></mrow></math>, producing a 1×3 vector <math aria-label="z"><mrow><mi>z</mi></mrow></math>. Each component of <math aria-label="z"><mrow><mi>z</mi></mrow></math> combines that component across four positions using the same attention weights.

<math display="block" aria-label="a (C U^V_1) = (a C) U^V_1 = z U^V_1"><mrow><mi>a</mi><mrow><mo>(</mo><mi>C</mi><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup><mo>)</mo></mrow><mo>=</mo><mrow><mo>(</mo><mi>a</mi><mi>C</mi><mo>)</mo></mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup><mo>=</mo><mi>z</mi><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math>

Applying <math aria-label="U_1^V"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math> to <math aria-label="z"><mrow><mi>z</mi></mrow></math> once therefore gives the same 1×2 output. For a linear transformation, applying the same projection at each position and then combining the results is equivalent to **combining first and applying that projection afterward**.

Assume the following latent vectors and attention weights. We retain <math aria-label="c3"><mrow><msub><mi>c</mi><mrow><mn>3</mn></mrow></msub></mrow></math> = [1, 2, 3] from the earlier example; the other positions and weights are chosen to check the computation.

| Token position | Latent vector | Weight |
| --- | --- | --- |
| <math aria-label="p0"><mrow><msub><mi>p</mi><mrow><mn>0</mn></mrow></msub></mrow></math> | [1, 0, 1] | 0.1 |
| <math aria-label="p1"><mrow><msub><mi>p</mi><mrow><mn>1</mn></mrow></msub></mrow></math> | [0, 1, 1] | 0.2 |
| <math aria-label="p2"><mrow><msub><mi>p</mi><mrow><mn>2</mn></mrow></msub></mrow></math> | [1, 1, 0] | 0.3 |
| <math aria-label="p3"><mrow><msub><mi>p</mi><mrow><mn>3</mn></mrow></msub></mrow></math> | [1, 2, 3] | 0.4 |

As for head 1 in the previous article, let <math aria-label="U_1^V"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math> produce [first component + third component, second component]. A's values are [2, 0], [1, 1], [1, 1], and [4, 2]. Their weighted sum using the table is [2.3, 1.3].

B combines the latent vectors first. The first component is 0.1×1 + 0.2×0 + 0.3×1 + 0.4×1 = 0.8. Computing the other components similarly gives <math aria-label="z"><mrow><mi>z</mi></mrow></math> = [0.8, 1.3, 1.5]. Applying <math aria-label="U_1^V"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math> gives [0.8 + 1.5, 1.3] = [2.3, 1.3], the same result.

Latent vectors are shared across heads, but the attention weights that combine them and the final value projection differ by head. Thus, <math aria-label="z"><mrow><mi>z</mi></mrow></math> and the final output are computed per-head. Also, **we have not moved softmax across a projection**. Scores and softmax still determine the weights; we only reorder the weighted sum with those weights and a linear projection.

## Combining with query and output projections

Figure 3 moved the key projection to the query, and Figure 4 moved the value projection after the weighted sum. Precombining these moved projections with the existing query or output projection is called **projection absorption**. The two projections shown separately for clarity can be computed as one matrix multiplication during inference.

The associativity shown so far also holds at a given computation step during training. In inference, learned weights are fixed, so consecutive projection matrices can be multiplied in advance and reused across tokens.

On the query side, consider <math aria-label="c_3^Q"><mrow><msubsup><mi>c</mi><mrow><mn>3</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math> → <math aria-label="U_1^Q"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math> → <math aria-label="q"><mrow><mi>q</mi></mrow></math> → transposed <math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> → <math aria-label="q tilde"><mrow><mover><mi>q</mi><mo>˜</mo></mover></mrow></math>. <math aria-label="U_1^Q"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math> is 3×2 and transposed <math aria-label="U_1^K"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">K</mi></msubsup></mrow></math> is 2×3, so pre-multiplying them gives a 3×3 matrix. Applying this composite matrix to <math aria-label="c_3^Q"><mrow><msubsup><mi>c</mi><mrow><mn>3</mn></mrow><mi mathvariant="normal">Q</mi></msubsup></mrow></math> produces <math aria-label="q tilde"><mrow><mover><mi>q</mi><mo>˜</mo></mover></mrow></math> directly, without separately constructing and then transforming the content query. The positional query path remains separate.

The value side extends similarly. Let <math aria-label="W_1^O"><mrow><msubsup><mi>W</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">O</mi></msubsup></mrow></math> denote head 1's portion of the [output projection that combines head outputs](/en/posts/attention-projections/). Here, it maps a two-component head output into the model dimension of 8, so <math aria-label="W_1^O"><mrow><msubsup><mi>W</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">O</mi></msubsup></mrow></math> has shape 2×8. Pre-multiplying <math aria-label="U_1^V"><mrow><msubsup><mi>U</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">V</mi></msubsup></mrow></math> and <math aria-label="W_1^O"><mrow><msubsup><mi>W</mi><mrow><mn>1</mn></mrow><mi mathvariant="normal">O</mi></msubsup></mrow></math> gives a 3×8 matrix. Applying it to <math aria-label="z"><mrow><mi>z</mi></mrow></math> directly yields head 1's 1×8 contribution to the model-dimensional output. Summing all heads' contributions gives the full output projection result.

This projection absorption is described in [DeepSeek-V2 §2.1.2](https://arxiv.org/html/2405.04434v5#S2.SS1.SSS2). If the weights change, the composite matrix must be recomputed. If normalization or a nonlinear operation lies between projections, we cannot skip it to combine them. Reordering floating-point computations can also introduce small rounding differences.

## Benefits and limits of reordering

Trace the work at the current <math aria-label="p3"><mrow><msub><mi>p</mi><mrow><mn>3</mn></mrow></msub></mrow></math> again. We build queries from the current input and add its KV latent vector and positional key to the cache. Each head uses its transformed query to read the four latent rows, computes content scores, and adds positional scores. Softmax weights combine the latent vectors, followed by the value and output projections.

This computation does not need to materialize all expanded per-head past K and V vectors as intermediates. But **reading past positions and computing attention scores and weighted sums still remain**. A longer context still adds cache rows.

A smaller stored representation does not make every computation lower-dimensional. The expanded content keys and values in our example are two-dimensional, while latents are three-dimensional. After reordering, content dot products and weighted sums operate on three-dimensional rather than two-dimensional vectors. We therefore need to consider changes in dot-product and weighted-sum computation alongside savings in KV reconstruction and memory use.

Actual runtime depends on context length, the number of requests, dimensions, kernels, and hardware. Prefill, which processes multiple queries together, need not choose the same computation path as decode, which processes one current query. The actual speedup from reordering must therefore be measured for the model and environment in use.

The previous article examined what to cache; this article examined how to compute attention from that cache. A shared latent representation reduces the cache, and reordering lets attention read it directly. Next, we will go beyond reading every position's representation and explore structures that restrict the range and choice of tokens attention reads.
