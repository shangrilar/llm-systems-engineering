LLM을 실행하는 데 필요한 것을 떠올리면 모델과 GPU가 먼저 생각납니다. 모델의 가중치를 GPU 메모리에 올리고 입력을 전달하면 결과가 나옵니다. 하지만 실제 시스템을 만들 때는 여기서 질문이 시작됩니다.

어떤 요청을 얼마나 빠르게 처리해야 할까요? 모델이 메모리에 들어가면 충분할까요? GPU를 늘리면 항상 더 효율적일까요?

이 연재에서는 **모델, 하드웨어, 워크로드**를 함께 보며 이런 질문에 답하려 합니다. 첫 글에서는 세 관점의 의미와 앞으로의 학습 경로를 정리합니다. 특정 장비의 성능을 측정한 글이 아니라, 이후 실험을 이해하기 위한 출발점입니다.

## 먼저, 토큰 하나가 나오는 과정을 생각해 봅시다

사용자가 “GPU는 왜 필요한가?”라는 문장을 보냈다고 가정해 봅시다. 텍스트는 토큰 ID로 바뀌고, 모델은 이 입력을 처리해 다음 토큰의 점수를 계산합니다. 생성 규칙에 따라 토큰 하나를 선택한 뒤, 다음 토큰을 생성하는 과정을 반복합니다.

이 과정에서 모델의 가중치를 읽고 행렬 연산을 수행하며, 중간 결과를 저장하거나 다시 사용합니다. 우리가 보는 문장은 이런 계산을 반복한 결과입니다.

그런데 사용자 한 명의 짧은 질문과 수백 명의 긴 문서 요청은 같은 실행 조건이 아닙니다. 같은 모델을 사용하더라도 관리할 데이터의 양, 기다리는 요청, 필요한 응답 속도가 달라집니다.

## 모델: 어떤 계산과 상태가 필요한가?

모델은 실행해야 할 계산의 구조를 정합니다. Transformer의 attention과 선형 계층, 계층 수와 차원, dense 모델인지 MoE인지 같은 선택이 여기에 속합니다.

여기서 **계산**과 **상태**를 함께 봅니다. 계산은 행렬곱이나 attention처럼 해야 할 일입니다. 상태는 그 계산에 필요해 보관하는 데이터입니다. 가중치는 대표적인 상태이고, 일반적인 자기회귀 Transformer 추론에서는 이전 토큰의 key와 value를 저장하는 KV cache도 중요합니다.

모델에 대해 처음 던질 질문은 다음과 같습니다.

- 입력을 처리하는 데 어떤 연산이 필요한가?
- 가중치와 중간 결과를 보관하는 데 얼마나 많은 메모리가 필요한가?
- 입력이나 출력이 길어지면 연산과 상태가 어떻게 늘어나는가?

“파라미터가 몇 개인가?”는 유용한 시작이지만, 전체 실행 비용을 결정하는 정보는 아닙니다. 입력 길이와 실제 실행 방식도 함께 확인해야 합니다.

## 하드웨어: 어디서, 어떻게 실행하는가?

이 블로그에서는 하드웨어라는 축에 **물리적 장치와 그 장치를 사용하는 시스템 소프트웨어**를 함께 포함합니다.

GPU의 연산 장치와 메모리, GPU 사이의 연결, 서버 사이의 네트워크가 물리적 기반입니다. 커널, 런타임, 메모리 관리, 병렬화와 스케줄링은 이 자원을 사용해 모델을 실행하는 방법입니다.

예를 들어 모델의 계산이 같더라도 중간 결과를 메모리에 여러 번 쓰고 읽는지, 여러 연산을 묶어 실행하는지에 따라 데이터 이동량이 달라질 수 있습니다. GPU가 여러 개라면 데이터를 어디에 두고 언제 교환할지도 정해야 합니다.

따라서 다음 질문을 함께 던집니다.

- 연산을 기다리는가, 데이터를 가져오기를 기다리는가?
- 메모리 용량이 부족한가, 데이터를 옮기는 속도가 제한적인가?
- GPU를 나눠 사용할 때 얻는 이점과 통신 비용은 무엇인가?

하드웨어 사양은 실행 조건을 이해하는 근거입니다. 실제 성능을 확인하려면 실행 경로와 측정 결과가 필요합니다.

## 워크로드: 어떤 조건에서 무엇을 달성해야 하는가?

워크로드는 시스템에 주어지는 일의 특성입니다. 이 블로그에서는 그 일을 수행하며 만족해야 할 요구사항도 함께 다룹니다.

추론이라면 입력·출력 길이, 동시 요청 수, 요청이 도착하는 패턴이 중요합니다. 요구사항에는 첫 응답까지 허용되는 시간, 생성 중 토큰 사이 간격, 품질과 비용 목표가 포함됩니다.

학습이라면 시퀀스 길이, 배치 구성, 학습 데이터 공급 방식 등이 실행 조건을 만듭니다. 목표 품질에 도달하는 시간과 비용, 중단 후 복구 같은 요구도 고려해야 합니다.

| 같은 모델을 사용하는 두 작업 | 실시간 대화 | 오프라인 대량 생성 |
| --- | --- | --- |
| 작업 조건 | 사용자가 응답을 기다림 | 준비된 입력을 묶어 처리 |
| 주요 요구 | 응답 지연과 품질 | 완료 기한, 처리량과 비용, 품질 |
| 설계할 때 확인할 것 | 대기열과 배치가 응답에 미치는 영향 | 자원을 충분히 쓰면서 기한을 지키는 방법 |

이 표는 어떤 설정이 항상 정답이라는 뜻이 아닙니다. 오프라인 작업에도 마감 시간이 있고, 실시간 서비스에도 비용 제약이 있습니다. **무엇을 측정하고 어떤 조건을 지켜야 하는지 먼저 정하자**는 뜻입니다.

## 세 관점을 연결하면 설계 질문이 됩니다

> 이 모델을, 이 하드웨어와 시스템에서, 이 워크로드에 맞게 실행하려면 어떤 선택을 해야 할까?

예를 들어 GPU 두 개로 모델을 나누는 상황을 생각해 봅시다.

모델 관점에서는 가중치와 실행 중 상태에 필요한 메모리를 확인합니다. 하드웨어 관점에서는 각 GPU의 메모리와 GPU 사이 연결을 확인합니다. 워크로드 관점에서는 요청 길이와 동시성, 허용 지연을 확인합니다.

그다음 모델을 어떻게 나눌지 정하고, 한 GPU에서 가능한 기준 설정과 비교합니다. 한 GPU에서 실행할 수 없다면 그 사실 자체가 중요한 제약입니다. 실행할 수 있다면 두 GPU로 나누는 이점이 추가된 통신 비용보다 큰지 측정해야 합니다.

이렇게 세 관점은 기술을 외우는 목록이 아니라 **선택의 근거를 찾는 질문**이 됩니다.

## 앞으로 배우는 순서

1. **기초:** 텐서와 모델의 계산이 GPU에서 어떻게 실행되는지 이해합니다. 작은 예제로 계산, 메모리, 측정의 의미를 익힙니다.
2. **추론:** 고정된 가중치로 토큰을 생성하고 여러 요청을 처리합니다. Prefill·decode, KV cache, batching과 scheduling을 연결합니다.
3. **학습:** Pretraining과 SFT를 통해 가중치를 갱신하는 구조를 배웁니다. Backward, gradient, optimizer state를 추가하고 여러 GPU로 확장합니다.
4. **RL 기반 Post-training:** 생성한 결과를 평가하고 정책을 갱신하는 구조를 배웁니다. Online RL에서는 추론과 학습 시스템이 하나의 과정으로 연결됩니다.

이는 이 블로그의 교육용 분류입니다. 일반적인 용어에서 SFT도 post-training에 포함됩니다. 여기서는 Pretraining과 SFT가 공유하는 학습 실행 구조를 먼저 설명하고, RL을 별도 과정으로 다룹니다.

각 과정에서 같은 세 관점을 반복해서 사용합니다. 기초를 쌓은 뒤에는 공개 모델과 시스템을 분석하는 특집에서 이 관점을 적용하겠습니다.

## 스스로 확인해 보기

- 같은 모델과 GPU라도 실시간 대화와 오프라인 생성에서 배치 설정이 달라질 수 있는 이유는 무엇인가요?
- “모델이 GPU 메모리에 들어간다”는 사실만으로 응답이 빠르다고 말할 수 있을까요?
- 성능이 좋아졌다는 결과를 볼 때 모델과 장비 외에 어떤 조건을 확인해야 할까요?

정확한 수치를 계산하기 전에도, 비교에 필요한 조건을 빠뜨리지 않는 것이 시작입니다. 다음 기초 글에서는 입력이 모델의 계산을 거쳐 다음 토큰으로 이어지는 과정을 더 작은 단위로 살펴볼 예정입니다.
