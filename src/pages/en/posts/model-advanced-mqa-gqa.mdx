In [Q·K·V projections](/en/posts/attention-projections/) and [Core Attention](/en/posts/core-attention/), we followed how each head gathers information using its own query, key, and value. In that arrangement, increasing the number of query heads also increases the number of corresponding key and value heads.

When generating tokens one at a time, we can store keys and values from earlier positions for reuse. As the context grows, however, there are more values to store. Could multiple queries use the same keys and values to reduce storage while preserving the computation that gathers information for each query?

This article first compares the sharing patterns of three structures. We then trace how one token leads to computation across multiple heads in MHA, before extending the example to MQA, where all query heads share KV, and GQA, where sharing occurs within groups. Finally, we examine exactly what becomes smaller, by how much, and the resulting trade-offs.

## Connecting queries to KV

**MHA** (Multi-Head Attention) uses a separate key head and value head for each query head. **MQA** (Multi-Query Attention) shares one key head and one value head across multiple query heads. **GQA** (Grouped-Query Attention) divides query heads into groups and shares keys and values within each group.

We will use **KV** to refer to keys and values together, and **one KV head** to mean a corresponding pair of one key head and one value head. The following figure compares four, two, and one KV heads while keeping four query heads.

In MHA each query reads its own numbered KV head. In GQA q1 and q2 share KA/VA, while q3 and q4 share KB/VB. In MQA all four queries share one K/V set. Each set represents cached positions p0 through p3." loading="lazy" /></picture></a>

The vectors <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> through <math aria-label="q4"><mrow><msub><mi>q</mi><mn>4</mn></msub></mrow></math> are **the query vectors computed by the current token's four query heads**. They are not queries from four different tokens. Each KV set below them represents the keys and values those queries will access. The arrows show which KV set each query uses.

In MHA, the mapping is one-to-one: <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> uses <math aria-label="K1/V1"><mrow><msub><mi>K</mi><mn>1</mn></msub><mo>/</mo><msub><mi>V</mi><mn>1</mn></msub></mrow></math>, <math aria-label="q2"><mrow><msub><mi>q</mi><mn>2</mn></msub></mrow></math> uses <math aria-label="K2/V2"><mrow><msub><mi>K</mi><mn>2</mn></msub><mo>/</mo><msub><mi>V</mi><mn>2</mn></msub></mrow></math>, and so on. In GQA, shown in the middle, <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> and <math aria-label="q2"><mrow><msub><mi>q</mi><mn>2</mn></msub></mrow></math> share <math aria-label="KA/VA"><mrow><msub><mi>K</mi><mi mathvariant="normal">A</mi></msub><mo>/</mo><msub><mi>V</mi><mi mathvariant="normal">A</mi></msub></mrow></math>, while <math aria-label="q3"><mrow><msub><mi>q</mi><mn>3</mn></msub></mrow></math> and <math aria-label="q4"><mrow><msub><mi>q</mi><mn>4</mn></msub></mrow></math> share <math aria-label="KB/VB"><mrow><msub><mi>K</mi><mi mathvariant="normal">B</mi></msub><mo>/</mo><msub><mi>V</mi><mi mathvariant="normal">B</mi></msub></mrow></math>. In MQA, all four queries use the same <math aria-label="K/V"><mrow><mi>K</mi><mo>/</mo><mi>V</mi></mrow></math>. **All three structures have four query heads; what changes is the number of KV heads and the scope of sharing.** This comparison redraws the [GQA paper's architecture diagram](https://arxiv.org/html/2305.13245v3#S2.SS2) with four query heads.

## MHA: separate KV for each head

Consider processing the current position <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math> in one layer. Positions <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math>, <math aria-label="p1"><mrow><msub><mi>p</mi><mn>1</mn></msub></mrow></math>, and <math aria-label="p2"><mrow><msub><mi>p</mi><mn>2</mn></msub></mrow></math> precede it, so there are four token positions to attend to, including the current position. The number after <math aria-label="p"><mrow><mi>p</mi></mrow></math> denotes **a position in the context**, rather than a token type or a head number.

For a small example, let the model dimension be 8, the number of query heads be 4, and the dimension of each head be 2. Keys and values also have two components per head. We will keep these conditions throughout the figures. These are illustrative dimensions, not measurements from an actual model.

<a href="/images/model-advanced-mqa-gqa/en/01-mha-per-head.png?v=68c1129c0deb" id="figure-1"><picture><source media="(max-width: 600px)" srcSet="/images/model-advanced-mqa-gqa/en/01-mha-per-head-mobile.png?v=e4bdf7daa99f" /><img src="/images/model-advanced-mqa-gqa/en/01-mha-per-head.png?v=68c1129c0deb" alt="The top shows input vectors at token positions p0 through p3, as one unsplit block each. The full vector at current position p3 is multiplied by WQ, WK, and WV. Below, rows are heads 1 through 4, showing their two-component queries, keys, and values at p3. Current keys and values join each head’s cache. Queries read their own cached positions p0 through p3. The remaining panels show head 1 attention and output concatenation." loading="lazy" /></picture></a>

In the first panel of Figure 1, each block from <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math> to <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math> represents **one input vector at that position**. It is the vector entering this layer, not a single vector component. We multiply the entire eight-component vector at the current position <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math> by three different weight matrices, <math aria-label="WQ"><mrow><msub><mi>W</mi><mi mathvariant="normal">Q</mi></msub></mrow></math>, <math aria-label="WK"><mrow><msub><mi>W</mi><mi mathvariant="normal">K</mi></msub></mrow></math>, and <math aria-label="WV"><mrow><msub><mi>W</mi><mi mathvariant="normal">V</mi></msub></mrow></math>, to produce Q, K, and V.

In this MHA example, each projection produces eight components. Grouping them into four heads with two components each gives <math aria-label="q1…q4"><mrow><msub><mi>q</mi><mn>1</mn></msub><mo>…</mo><msub><mi>q</mi><mn>4</mn></msub></mrow></math>, <math aria-label="k1…k4"><mrow><msub><mi>k</mi><mn>1</mn></msub><mo>…</mo><msub><mi>k</mi><mn>4</mn></msub></mrow></math>, and <math aria-label="v1…v4"><mrow><msub><mi>v</mi><mn>1</mn></msub><mo>…</mo><msub><mi>v</mi><mn>4</mn></msub></mrow></math>. Each small cell below represents one vector component, and each row represents one head. For example, <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math>, <math aria-label="k1"><mrow><msub><mi>k</mi><mn>1</mn></msub></mrow></math>, and <math aria-label="v1"><mrow><msub><mi>v</mi><mn>1</mn></msub></mrow></math> are all **vectors for Head 1 at the current position**. We do not first split the input vector into four pieces and send one piece to each head. Each head projects the entire input using different weights.

Suppose we have kept the keys and values for <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math> through <math aria-label="p2"><mrow><msub><mi>p</mi><mn>2</mn></msub></mrow></math> before computing the current position. This storage of keys and values from processed positions is the **KV cache**. Adding the newly computed <math aria-label="k1"><mrow><msub><mi>k</mi><mn>1</mn></msub></mrow></math> and <math aria-label="v1"><mrow><msub><mi>v</mi><mn>1</mn></msub></mrow></math> to Head 1's cache leaves <math aria-label="K1"><mrow><msub><mi>K</mi><mn>1</mn></msub></mrow></math> and <math aria-label="V1"><mrow><msub><mi>V</mi><mn>1</mn></msub></mrow></math> containing four positions, from <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math> through <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math>. The other heads add their current-position values in the same way.

Here, lowercase <math aria-label="k1"><mrow><msub><mi>k</mi><mn>1</mn></msub></mrow></math> and <math aria-label="v1"><mrow><msub><mi>v</mi><mn>1</mn></msub></mrow></math> denote vectors at the current position, while uppercase <math aria-label="K1"><mrow><msub><mi>K</mi><mn>1</mn></msub></mrow></math> and <math aria-label="V1"><mrow><msub><mi>V</mi><mn>1</mn></msub></mrow></math> denote matrices collecting multiple positions. Each matrix is **four positions × two components per head**, or <math aria-label="4 × 2"><mrow><mn>4</mn><mo>×</mo><mn>2</mn></mrow></math>. Moving down one row means moving to the next token position; switching from <math aria-label="K1"><mrow><msub><mi>K</mi><mn>1</mn></msub></mrow></math> to <math aria-label="K2"><mrow><msub><mi>K</mi><mn>2</mn></msub></mrow></math> means using another head's representation.

The third panel expands Head 1's computation. Taking the dot product of the two-component <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> with each of the four rows of <math aria-label="K1"><mrow><msub><mi>K</mi><mn>1</mn></msub></mrow></math> produces four position scores. Applying the [scaling and softmax described in Core Attention](/en/posts/core-attention/) produces four weights that sum to 1. The current position <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math> can attend to every position from <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math> through itself.

Using those weights to take a weighted sum of the four rows of <math aria-label="V1"><mrow><msub><mi>V</mi><mn>1</mn></msub></mrow></math> gives the two-component output <math aria-label="o1"><mrow><msub><mi>o</mi><mn>1</mn></msub></mrow></math>. Here, the weights are **the proportions determined by this query for incorporating the value at each position**. They are distinct from the learned parameters <math aria-label="WQ"><mrow><msub><mi>W</mi><mi mathvariant="normal">Q</mi></msub></mrow></math>, <math aria-label="WK"><mrow><msub><mi>W</mi><mi mathvariant="normal">K</mi></msub></mrow></math>, and <math aria-label="WV"><mrow><msub><mi>W</mi><mi mathvariant="normal">V</mi></msub></mrow></math> used to produce Q, K, and V.

The other three heads similarly compute <math aria-label="o2"><mrow><msub><mi>o</mi><mn>2</mn></msub></mrow></math>, <math aria-label="o3"><mrow><msub><mi>o</mi><mn>3</mn></msub></mrow></math>, and <math aria-label="o4"><mrow><msub><mi>o</mi><mn>4</mn></msub></mrow></math> using their own queries and KV. Concatenating the four outputs gives <math aria-label="2 + 2 + 2 + 2 = 8"><mrow><mn>2</mn><mo>+</mo><mn>2</mn><mo>+</mo><mn>2</mn><mo>+</mo><mn>2</mn><mo>=</mo><mn>8</mn></mrow></math> components, which the output projection <math aria-label="WO"><mrow><msub><mi>W</mi><mi mathvariant="normal">O</mi></msub></mrow></math> combines. Labels such as <math aria-label="a1"><mrow><msub><mi>a</mi><mn>1</mn></msub></mrow></math> and <math aria-label="b1"><mrow><msub><mi>b</mi><mn>1</mn></msub></mrow></math> in the figure represent the two components of each output vector.

Keys and values from past positions are reused when computing the next position, but past queries do not need to be stored in this KV cache. The new position's query reads the stored keys and values. We can now consider reducing the number of KV sets stored in this computation.

## MQA: sharing KV across all queries

In MHA, each head produced its own keys and values at every position. **MQA produces one key vector and one value vector per position and shares them across all query heads.** Queries are still produced separately for each head.

At the current position <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math>, the Q projection still produces four queries with two components each. The K and V projections, however, each produce only two components. With a model dimension of 8, this configuration has an <math aria-label="8 × 8"><mrow><mn>8</mn><mo>×</mo><mn>8</mn></mrow></math> matrix <math aria-label="WQ"><mrow><msub><mi>W</mi><mi mathvariant="normal">Q</mi></msub></mrow></math> and <math aria-label="8 × 2"><mrow><mn>8</mn><mo>×</mo><mn>2</mn></mrow></math> matrices <math aria-label="WK"><mrow><msub><mi>W</mi><mi mathvariant="normal">K</mi></msub></mrow></math> and <math aria-label="WV"><mrow><msub><mi>W</mi><mi mathvariant="normal">V</mi></msub></mrow></math>.

<a href="/images/model-advanced-mqa-gqa/en/02-mqa-different-outputs.png?v=1c4191ca34f3" id="figure-2"><picture><source media="(max-width: 600px)" srcSet="/images/model-advanced-mqa-gqa/en/02-mqa-different-outputs-mobile.png?v=e3886471a31a" /><img src="/images/model-advanced-mqa-gqa/en/02-mqa-different-outputs.png?v=1c4191ca34f3" alt="Four queries share one 4×2 K and V set. Each query runs its own attention computation, producing outputs o1 through o4." loading="lazy" /></picture></a>

The left side of Figure 2 contains one K matrix and one V matrix, each of size <math aria-label="4 × 2"><mrow><mn>4</mn><mo>×</mo><mn>2</mn></mrow></math>. **Having one KV head does not mean storing only one token position.** The shared K and V still contain values for all four positions, from <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math> through <math aria-label="p3"><mrow><msub><mi>p</mi><mn>3</mn></msub></mrow></math>.

On the right, <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> computes scores using the four rows of K, applies softmax, and takes a weighted sum of V to produce <math aria-label="o1"><mrow><msub><mi>o</mi><mn>1</mn></msub></mrow></math>. The query <math aria-label="q2"><mrow><msub><mi>q</mi><mn>2</mn></msub></mrow></math> uses the same K and V, but its different query vector can produce different position scores and weighting proportions. For example, one query may give more weight to the value at <math aria-label="p0"><mrow><msub><mi>p</mi><mn>0</mn></msub></mrow></math>, while another gives more weight to the value at <math aria-label="p2"><mrow><msub><mi>p</mi><mn>2</mn></msub></mrow></math>.

Thus, **sharing the same KV does not force the outputs to be identical.** Each of the four queries performs its own attention computation and produces its own output. The four Attention boxes distinguish these computation relationships; they do not require four separate kernel launches. As in MHA, the outputs are concatenated and passed to the output projection.

Storage changes substantially. MHA stores four sets of K and V, while MQA stores just one. In this example, that is <math aria-label="K 4 × 2 + V 4 × 2 = 16"><mrow><mi>K</mi><mn>4</mn><mo>×</mo><mn>2</mn><mo>+</mo><mi>V</mi><mn>4</mn><mo>×</mo><mn>2</mn><mo>=</mo><mn>16</mn></mrow></math> components. By sharing KV across heads, MQA reduces the amount of KV to store and read during token-by-token generation. [MQA paper](https://arxiv.org/abs/1911.02150)

## GQA: sharing KV within groups

GQA defines the scope of KV sharing by group. If we divide four queries into two groups, the first contains <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> and <math aria-label="q2"><mrow><msub><mi>q</mi><mn>2</mn></msub></mrow></math>, and the second contains <math aria-label="q3"><mrow><msub><mi>q</mi><mn>3</mn></msub></mrow></math> and <math aria-label="q4"><mrow><msub><mi>q</mi><mn>4</mn></msub></mrow></math>. Each group uses a separate K and V.

<a href="/images/model-advanced-mqa-gqa/en/03-gqa-groups.png?v=83024d124701" id="figure-3"><picture><source media="(max-width: 600px)" srcSet="/images/model-advanced-mqa-gqa/en/03-gqa-groups-mobile.png?v=ee5a41af1713" /><img src="/images/model-advanced-mqa-gqa/en/03-gqa-groups.png?v=83024d124701" alt="q1 and q2 share KA/VA; q3 and q4 share KB/VB. Each K and V is 4×2. Each query runs its own attention computation, producing outputs o1 through o4." loading="lazy" /></picture></a>

In Figure 3, <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> and <math aria-label="q2"><mrow><msub><mi>q</mi><mn>2</mn></msub></mrow></math> both read <math aria-label="KA/VA"><mrow><msub><mi>K</mi><mi mathvariant="normal">A</mi></msub><mo>/</mo><msub><mi>V</mi><mi mathvariant="normal">A</mi></msub></mrow></math>, while <math aria-label="q3"><mrow><msub><mi>q</mi><mn>3</mn></msub></mrow></math> and <math aria-label="q4"><mrow><msub><mi>q</mi><mn>4</mn></msub></mrow></math> both read <math aria-label="KB/VB"><mrow><msub><mi>K</mi><mi mathvariant="normal">B</mi></msub><mo>/</mo><msub><mi>V</mi><mi mathvariant="normal">B</mi></msub></mrow></math>. Each group's KV contains all four positions. **The groups divide query heads, not the token positions stored in the cache.**

At the current position, the Q projection still produces four queries with two components each. The K and V projections each produce two heads with two components each. In this example, <math aria-label="WK"><mrow><msub><mi>W</mi><mi mathvariant="normal">K</mi></msub></mrow></math> and <math aria-label="WV"><mrow><msub><mi>W</mi><mi mathvariant="normal">V</mi></msub></mrow></math> are each <math aria-label="8 × 4"><mrow><mn>8</mn><mo>×</mo><mn>4</mn></mrow></math>, and each KV head adds its newly computed values to its corresponding cache.

Within a group, sharing works as in MQA. The queries <math aria-label="q1"><mrow><msub><mi>q</mi><mn>1</mn></msub></mrow></math> and <math aria-label="q2"><mrow><msub><mi>q</mi><mn>2</mn></msub></mrow></math> read the same KV but gather values using their own computed proportions. The second group follows the same process. There are still four outputs, <math aria-label="o1"><mrow><msub><mi>o</mi><mn>1</mn></msub></mrow></math> through <math aria-label="o4"><mrow><msub><mi>o</mi><mn>4</mn></msub></mrow></math>, but only two KV sets to store. Total storage is <math aria-label="2 × 16 = 32"><mrow><mn>2</mn><mo>×</mo><mn>16</mn><mo>=</mo><mn>32</mn></mrow></math> components.

Let <math aria-label="hq"><mrow><msub><mi>h</mi><mi>q</mi></msub></mrow></math> denote the number of query heads and <math aria-label="hkv"><mrow><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub></mrow></math> the number of KV heads. In the usual configuration with equally sized groups, <math aria-label="hq / hkv"><mrow><msub><mi>h</mi><mi>q</mi></msub><mo>/</mo><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub></mrow></math> query heads share each KV head. In this example, that is <math aria-label="4 / 2 = 2"><mrow><mn>4</mn><mo>/</mo><mn>2</mn><mo>=</mo><mn>2</mn></mrow></math>. Setting <math aria-label="hkv = 1"><mrow><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub><mo>=</mo><mn>1</mn></mrow></math> gives MQA's sharing pattern; setting <math aria-label="hkv = hq"><mrow><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub><mo>=</mo><msub><mi>h</mi><mi>q</mi></msub></mrow></math> gives MHA's. GQA adjusts the degree of sharing between these two endpoints. [GQA paper, Section 2.2](https://arxiv.org/html/2305.13245v3#S2.SS2)

## KV head count and storage

We can now compare the three KV caches using equally sized cells. Each cell represents one stored component. All three configurations have four token positions and two components per head for both K and V.

<a href="/images/model-advanced-mqa-gqa/en/04-kv-storage-axis.png?v=d764489c02d9" id="figure-4"><picture><source media="(max-width: 600px)" srcSet="/images/model-advanced-mqa-gqa/en/04-kv-storage-axis-mobile.png?v=c66e7e09b22c" /><img src="/images/model-advanced-mqa-gqa/en/04-kv-storage-axis.png?v=d764489c02d9" alt="Equal-size cells compare KV caches at T=4. Each KV head has four rows, p0 through p3, with two key and two value components each. MHA has four heads and 64 components; GQA two heads and 32; MQA one head and 16." loading="lazy" /></picture></a>

In MHA, each of the four KV heads has eight key components and eight value components, giving 64 components in total. GQA has two KV heads and 32 components; MQA has one KV head and 16. **This reduction comes from storing fewer separate KV heads, while preserving the number of token positions and components per head.**

For one request in one layer, we can generalize this as follows. Here, <math aria-label="T"><mrow><mi>T</mi></mrow></math> is the number of token positions in the cache, <math aria-label="hkv"><mrow><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub></mrow></math> is the number of KV heads, and <math aria-label="dh"><mrow><msub><mi>d</mi><mi>h</mi></msub></mrow></math> is the dimension per head. We assume equal head dimensions for K and V.

<math display="block" aria-label="Stored KV components = 2 × T × h_kv × d_h"><mrow><mtext>Stored KV components</mtext><mo>=</mo><mn>2</mn><mo>×</mo><mi>T</mi><mo>×</mo><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub><mo>×</mo><msub><mi>d</mi><mi>h</mi></msub></mrow></math>

The leading 2 accounts for storing both K and V. Substituting the MHA example gives <math aria-label="2 × 4 × 4 × 2 = 64"><mrow><mn>2</mn><mo>×</mo><mn>4</mn><mo>×</mo><mn>4</mn><mo>×</mo><mn>2</mn><mo>=</mo><mn>64</mn></mrow></math>. For GQA and MQA, only <math aria-label="hkv"><mrow><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub></mrow></math> changes, to 2 and 1 respectively. With the other conditions and storage size per component held equal, GQA's KV storage relative to MHA is <math aria-label="hkv / hq"><mrow><msub><mi>h</mi><mi mathvariant="normal">kv</mi></msub><mo>/</mo><msub><mi>h</mi><mi>q</mi></msub></mrow></math>. In this example, GQA uses half as much storage and MQA uses one quarter.

This expression counts the KV values themselves. For an entire model, storage must be summed across layers; for multiple requests, it must also be summed across requests. Actual memory allocation may include additional space depending on the implementation.

Even with sharing, each query computes scores against the keys at the positions it attends to and takes a weighted sum of their values. Keeping the number of query heads and the context length unchanged leaves this core attention arithmetic at the same scale. Meanwhile, the output size of KV projections and the amount of KV to store decrease. An implementation that reuses shared KV effectively can also reduce the amount of data fetched from memory.

Consequently, **reducing the cache to one quarter of its size does not necessarily reduce total execution time to one quarter.** Other operations, model-weight reads, and how the kernel reuses KV also affect runtime. The figures 64, 32, and 16 in this article compare stored component counts.

## Choosing a sharing scope

MHA can learn separate key and value representations for each query head. MQA requires all queries to use the same key and value representations; GQA applies that constraint within each group. Broader KV sharing reduces storage, but also reduces the freedom to produce different keys and values for different heads.

For this reason, arbitrarily combining KV at runtime in a model trained with MHA does not preserve its outputs. MQA and GQA are model structures with different KV projections and head connections. The GQA paper presents a method that converts the KV projections of an existing MHA checkpoint and then performs additional training. In its experiments, it reports GQA quality close to MHA and speed close to MQA. Those results apply to the paper's models and training and execution conditions. [GQA paper, Sections 2–3](https://arxiv.org/html/2305.13245v3#S2)

When reading an actual model configuration, therefore, check both the query-head count and the KV-head count. Their ratio helps explain the sharing scope and KV storage, while quality and speed must be evaluated with the model trained for that structure and its execution environment.

We have examined how to change KV sharing while preserving per-query computation and outputs. The next article moves beyond the scope of sharing to consider **making the stored KV representation itself smaller**.
