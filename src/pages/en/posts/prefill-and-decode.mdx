In [Inference and the KV Cache](/en/posts/inference-kv-cache/), we followed how processing the input context selects the first output token, after which new tokens enter the model while past K/V is reused. Both stages execute the same model’s forward pass, but they present different shapes of work to the GPU. The first computes several input positions together; an ordinary generation step computes one new position per request.

Understanding this difference explains why token generation with a small batch is often limited by memory bandwidth. We will first distinguish positions computed now from the context attention accesses. We will then separate weight reuse from KV reads and examine the conditions under which computation or data movement becomes the bottleneck. Our baseline is a dense Transformer with fixed weights and ordinary autoregressive generation.

## How many tokens enter the same model

During **prefill**, which first processes the input context, the model can compute several supplied tokens together. With input p0·p1·p2·p3, it computes representations at four positions and uses the logits at the final position to select the first output token, x0. The causal mask remains in place, so computation at p1 does not attend to the future input p2.

During the subsequent **decode**, the model processes x0 as new input and selects x1. The next execution receives x1. We cannot feed an as-yet unselected x2 into the current execution, so generation within a request has a sequential dependency.

Here, one token means **one token per request**. If eight requests all participate in decode, the execution processes eight new positions in total. It does not mean the entire batch processes only one token. We will treat methods that verify several candidates together, such as speculative decoding, separately as extensions of this basic loop.

[![Prefill computes Q for multiple input positions together. Decode computes Q for one new position per request, attending to that request’s accumulated K/V.](/images/prefill-and-decode/en/01-token-positions.png)](/images/prefill-and-decode/en/01-token-positions.png)

In the figure, T is the number of token positions computed in the current execution, and L is the context length a request attends to. Their values may be equal, but they generally mean different things. A single basic prefill request has T=L; a single decode request has T=1 while L can be in the thousands.

## Compute new positions and attend to past context

We can divide Transformer operations into two groups. Q/K/V projections, the attention output projection, and MLPs apply the same weights to the vector at each token position. Normalization and residual connections are also performed per token in the model assumed here. Decode with a KV cache **runs these operations on the new position**. It does not rerun MLPs over every past position at each step. Calling an operation token-wise does not mean its input vector contains no context information: that vector already reflects context incorporated by earlier attention.

By contrast, attention’s QKᵀ and AV combine information across positions. The current position’s Q uses both previously stored K/V and the current position’s K/V. Even with just one newly computed token, a longer context therefore increases attention’s work. [The Transformers cache explanation](https://huggingface.co/docs/transformers/cache_explanation) shows how current K/V is combined with the past cache so the new Q can attend to the accumulated context.

Showing only one head with dimension d gives the following shapes. L includes the current input position.

```text
One basic prefill request:
Q [L, d] × Kᵀ [d, L] → logical score shape [L, L]

One ordinary decode request:
Q [1, d] × Kᵀ [d, L] → logical score shape [1, L]
```

Prefill’s causal mask excludes future positions. These are also logical computational shapes; they do not mean the entire score matrix must be stored in GPU memory. [FlashAttention](/en/posts/flash-attention/) uses this distinction to reduce memory traffic from large intermediate arrays.

Suppose eight requests each attend to a context of 2,048 tokens, including the current position. Before execution, each request has KV for 2,047 past positions, to which it adds K/V for one new input. Projections and MLPs compute eight new positions in total, while attention accesses 2,048 positions within each request’s own context. **Understanding the full workload requires both T for token-wise operations and L for attention.**

## Computation per set of weights read

We can write a token-wise linear operation as follows. Here, d_in and d_out are the input and output vector dimensions.

```text
X [T, d_in] × W [d_in, d_out] → Y [T, d_out]
```

Increasing T adds output rows without changing the size of W. After fetching a weight value, the operation can reuse it across several input rows. From the perspective of this linear operation, grouping one request’s prefill tokens or several requests’ decode tokens both create opportunities for reuse.

[![The same-sized weights W are used to compute one token or four tokens. Processing more tokens together increases computation relative to weight reads.](/images/prefill-and-decode/en/02-weight-reuse.png)](/images/prefill-and-decode/en/02-weight-reuse.png)

[Arithmetic intensity](/en/posts/gpu-arithmetic-intensity-and-fusion/) describes how much computation is performed relative to the data moved. Counting a multiplication and an addition as one FLOP each, and storing each weight element in s bytes, gives this simple view of the linear operation:

```text
Computation ≈ 2 × T × d_in × d_out FLOPs
Weight data = s × d_in × d_out bytes

Approximation when weight reads dominate:
Computation / weight data ≈ 2T/s FLOP/byte
```

This approximation counts one read of the weights and omits input/output traffic and the effects of tiling and caching in a real kernel. It is neither the exact arithmetic intensity of the entire model nor a measured execution speed. [NVIDIA’s matrix multiplication performance guide](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html) likewise estimates bottlenecks by comparing the ratio of computation to data movement with the hardware’s ratio of compute performance to bandwidth.

For an illustrative linear layer with d_in=d_out=4,096 and two bytes per element, W occupies 32 MiB. Let us vary only T in this single-layer example. GFLOPs means a billion FLOPs, while MiB means 2²⁰ bytes.

| Tokens processed now, T | Computation | Weight data | Approximate ratio counting weights alone |
| --- | --- | --- | --- |
| 1 | About 0.0336 GFLOPs | 32 MiB | 1 FLOP/byte |
| 8 | About 0.2684 GFLOPs | 32 MiB | 8 FLOP/byte |
| 128 | About 4.2950 GFLOPs | 32 MiB | 128 FLOP/byte |

Counting one transfer each of the input and output lowers the last row’s ratio to about 120.47 FLOP/byte. As T grows, the approximation that omits input/output traffic becomes less accurate. The intuition to retain is that **using the same weights for more tokens increases the computation performed relative to the weights read**.

## Why reads matter in small decode batches

The GPU’s compute units need weights and inputs before they can work. When a model is larger than the on-chip cache and weights must continually arrive from HBM, processing just one new token reads many weights while performing little computation per value. Faster compute units will not reduce total execution time proportionally if data cannot arrive quickly enough. This is the first reason small-batch decode is often limited by memory bandwidth.

The second source of reads is KV. We no longer need to recompute past K/V, but we still need to access it to calculate attention for the current Q. Longer contexts increase both the data read and the attention computation. Caching replaces recomputation with storage and reads. During decode, a query head has only one new Q, leaving little opportunity to reuse the past K/V it reads across multiple new positions. Increasing context length alone does not increase that reuse.

[![Weights are reused across new-token computation for multiple requests, while each request’s KV represents its own context. Memory bandwidth limits and insufficient storage capacity are separate issues.](/images/prefill-and-decode/en/03-memory-reads.png)](/images/prefill-and-decode/en/03-memory-reads.png)

Requests A, B, and C share weights W. In our baseline, however, A reads KV(A), B reads KV(B), and C reads KV(C). Grouping more requests increases reuse of W without merging all their KV reads into a single shared context. We must therefore distinguish cases dominated by weight reads from those where long-context KV reads contribute substantially. [The JAX Scaling Book’s inference analysis](https://jax-ml.github.io/scaling-book/inference/) also analyzes the weight cost of linear operations separately from the KV cost of attention.

The memory issue here is **the speed at which data can be fetched**. It differs from lacking enough space to store KV. Growing context can affect both, but reducing a reading bottleneck and finding storage capacity require separate consideration.

## Bottleneck conditions and the move to batching

Prefill can reuse weights across many input tokens, making it easier to use the available compute performance. With enough tokens computed together, finishing the arithmetic may take longer than supplying the data. The same explanation does not automatically apply to very short inputs or small executions, however.

Larger decode batches also increase reuse in linear operations. Longer contexts, on the other hand, can increase the share of time spent reading KV. The boundary also depends on GQA’s reduced number of KV heads, data precision, GPU bandwidth and compute performance, and the efficiency of the actual kernels. Different operations can have different bottlenecks, so rather than assigning one label to all inference, we should examine **which part takes time under which execution conditions**.

A request must wait for its next token, but new inputs from other requests may already be ready. Computing them together can increase weight reuse. The problem then extends beyond collecting more tokens: we must decide how long requests of different lengths and arrival times should wait, and which resources their execution may use. [Batching and Scheduling](/en/posts/batching-and-scheduling/) examines those decisions.
