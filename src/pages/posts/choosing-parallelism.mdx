여러 병렬화 방법을 알고 나면 다음 질문은 “어떤 것을 켤까?”입니다. 그러나 이름부터 고르기보다, **무엇이 지금 실행을 막고 있고 어떤 결과를 개선해야 하는지**에서 출발하는 편이 좋습니다. 메모리에 들어가지 않는 문제와, 한 요청이 느린 문제와, 많은 요청이 쌓이는 문제는 서로 다른 배치를 요구할 수 있습니다.

이 글에서는 GPU 네 개를 세 가지 방식으로 배치합니다. 먼저 각 GPU의 메모리에 필요한 데이터가 들어가는지 확인하고, 가능한 배치에서 응답 시간과 처리량을 비교하는 방법을 살펴보겠습니다. 마지막에는 연결 구조와 다른 병렬화 방법을 결합하고, 실행을 바꾼 뒤 다시 측정할 항목을 정리합니다.

## 같은 GPU를 다른 크기의 그룹으로 묶기

고정된 가중치로 독립 요청을 처리하는 dense 모델을 생각해 보겠습니다. GPU마다 모델 한 벌을 두면 복제본 네 개가 생깁니다. 두 GPU로 모델 한 벌을 나누고 그 묶음을 두 벌 만들 수도 있습니다. 네 GPU가 한 모델 실행을 함께 맡는 배치도 가능합니다.

[![4개 단일 GPU 복제본, 2개의 2-GPU TP 복제본, 1개의 4-GPU TP 복제본을 비교합니다.](/images/choosing-parallelism/01-layouts.png)](/images/choosing-parallelism/01-layouts.png)

두 GPU 묶음 두 벌의 예에서는 GPU 0·1이 TP 그룹 하나이고 2·3이 다른 TP 그룹입니다. 각 그룹 안에서는 같은 요청을 계산하기 위해 통신하지만, 두 복제본 사이에는 서로 다른 요청을 배분합니다. 이것이 이 예에서의 TP 2 × DP 2입니다.

그룹 크기가 커지면 한 모델의 가중치와 일부 계산을 더 나눌 수 있지만, 같은 네 GPU에서 운영할 독립 복제본 수는 줄어듭니다. 한 GPU에 하나의 모델을 복제하던 경우와 비교할 때, 요청 하나에 사용하는 자원과 동시에 운영할 모델 묶음을 함께 봐야 합니다. 실제 프레임워크의 설정 이름은 모델 부분별 그룹 의미와 다를 수 있으므로, 여기서는 도형 안의 실제 배치를 기준으로 읽겠습니다.

## 실행 가능한 배치를 메모리로 거르기

GPU당 사용 가능한 메모리를 24 GiB, 모델 가중치를 32 GiB로 두겠습니다. GiB는 2의 거듭제곱 기준의 메모리 용량 단위입니다. 이 예에서는 가중치를 TP 크기에 맞춰 균등하게 나눌 수 있고, 각 GPU에서 요청 상태·활성값·통신 버퍼와 기타 공간에 총 8 GiB가 추가로 필요하다고 가정합니다.

[![24GiB GPU와 32GiB 모델에서 추가 상태 8GiB를 포함하면 세 배치가 각각 40,24,16GiB를 사용합니다.](/images/choosing-parallelism/02-memory.png)](/images/choosing-parallelism/02-memory.png)

복제본 네 개의 배치는 각 GPU에 가중치만 32 GiB가 필요하므로 제외됩니다. GPU 네 개의 메모리 합이 96 GiB여도 각각의 GPU에 필요한 값이 들어가야 합니다. 여러 GPU의 메모리가 자동으로 하나의 큰 메모리가 되는 것은 아닙니다.

TP 2는 가중치 16 GiB와 추가 공간 8 GiB로 24 GiB를 사용합니다. 계산상 맞지만 여유가 없어 입력 증가나 순간 사용량에 취약합니다. TP 4는 16 GiB를 사용해 8 GiB가 남습니다. 따라서 이 가정에서는 TP 4를 검토할 이유가 있지만, 아직 더 빠르다는 결론은 낼 수 없습니다.

이는 **용량 계산을 위한 가정이며 실제 모델의 메모리 측정값이 아닙니다.** 실제 추가 공간은 배치, 문맥 길이, TP 크기와 구현에 따라 달라집니다. 가중치를 모두 균등 분할하지 못할 수도 있습니다. 단일 요청으로 로딩에 성공했는지뿐 아니라 목표 워크로드를 실행할 때의 최고 사용량을 확인해야 합니다.

## 응답 시간과 처리량의 목표를 함께 놓기

메모리에 들어가는 후보들 중 어떤 배치가 유리할까요? TP로 한 요청의 계산을 나누면 빨라질 수 있지만, 연산 사이의 통신과 대기가 늘어납니다. TP 4가 TP 2보다 반드시 빠른 것은 아닙니다. 반대로 복제본을 더 많이 두면 서로 다른 요청을 처리할 여지가 늘지만, 각 복제본의 실행 시간이 길거나 요청이 부족하면 기대한 이득을 얻지 못합니다.

[![요청의 대기와 실행 시간을 구별하고 메모리, 응답 시간 분포, 처리량을 같은 조건에서 측정합니다.](/images/choosing-parallelism/03-goals.png)](/images/choosing-parallelism/03-goals.png)

사용자가 보는 응답 시간은 요청 도착부터 완료까지이며 대기열에 머문 시간도 포함합니다. 처리량은 단위 시간에 완료한 작업량입니다. 요청 길이가 다르면 요청 수만 비교하지 말고 입력·출력 토큰 수도 함께 맞춰야 합니다. 토큰을 순차 생성하는 서비스라면 첫 결과가 나오는 시간과 이후 결과가 나오는 간격도 구별해 볼 수 있습니다.

두 GPU 묶음 두 벌에서 묶음 하나의 지속 처리량을 q₂, 네 GPU 묶음 한 벌의 처리량을 q₄라고 해보겠습니다. 입력이 충분하고 복제본 사이에 추가 경합이 없다면 전자의 전체 처리량은 대략 2q₂입니다. 하지만 **q₄가 2q₂보다 큰지는 측정하기 전에는 알 수 없습니다.** 또한 높은 처리량을 얻으려고 대기를 길게 허용했다면 응답 시간 목표를 위반할 수 있습니다.

그래서 먼저 허용할 응답 시간과 입력 조건을 정하고, 그 조건을 만족하는 범위의 지속 처리량을 비교해야 합니다. 평균만 좋고 일부 요청이 매우 늦는 경우를 놓치지 않도록 응답 시간의 분포도 확인합니다. 메모리가 부족해 실패한 배치는 속도 순위에 올리기 전에 해결해야 합니다.

## 연결 구조와 병렬화의 조합 맞추기

GPU 0·1 사이와 2·3 사이의 연결이 빠르고 두 묶음 사이가 상대적으로 느리다면, 반복 통신이 많은 TP를 각 묶음 안에 두는 후보를 생각할 수 있습니다. 같은 TP 크기라도 어느 GPU들이 그룹을 이루느냐에 따라 공유 링크와 통신 비용이 달라집니다. [Ring과 Tree](/posts/collective-ring-tree/)에서 본 논리적 관계와 실제 연결의 구별이 다시 필요합니다.

다른 병렬화는 남은 문제에 맞춰 결합합니다. TP 구간 주변의 활성값 복제가 부담이면 SP, 긴 문맥의 어텐션과 활성값이 부담이면 CP를 검토합니다. 층별로 모델을 나누어 담으려면 PP를 고려하되 파이프라인을 채울 입력과 단계 균형이 필요합니다. MoE 모델에서는 EP로 Expert를 나눌 수 있으며 라우팅 분포와 토큰 교환을 함께 봅니다.

이 방법들의 크기를 모두 독립적으로 곱하면 GPU 수가 된다고 가정하지는 않습니다. 예를 들어 앞서 본 SP는 기존 TP 그룹의 활성값 배치를 바꾸는 방식이었습니다. 조합을 적을 때는 어떤 GPU가 어떤 그룹에 참여하며 무엇을 복제·분할하는지 실제 배치부터 그리는 편이 정확합니다.

## 배치를 바꾼 뒤 병목 다시 확인하기

비교 실험에서는 모델과 정밀도, 입력·출력 길이의 분포, 요청 도착 패턴, GPU와 연결, 실행 소프트웨어를 기록해야 합니다. 배치 방식에 맞춰 조정한 실행 설정도 남기고, 초기 준비 시간과 안정된 실행 구간을 구별합니다. 조건을 바꾼 비교라면 어느 차이의 효과인지 함께 설명해야 합니다.

각 후보에서는 최고 메모리 사용량, 응답 시간 분포, 지속 처리량과 실패 여부를 확인합니다. 이어 실행 시간선을 보며 계산을 기다리는지, 데이터 전달이 늦는지, 일부 참여자에게 작업이 몰렸는지 살펴봅니다. 겹쳐 실행된 계산과 통신 시간을 단순 합산하면 전체 시간을 잘못 설명할 수 있습니다.

[연산 최적화에서 모델 전체 성능으로](/posts/model-performance-and-bottlenecks/)에서는 개선 뒤 병목이 옮겨갈 수 있음을 봤습니다. GPU 배치도 같습니다. 계산을 나눈 다음에는 통신이, 메모리 여유를 만든 다음에는 요청 대기가 더 큰 문제가 될 수 있습니다. **목표를 만족하도록 배치를 정하고, 바뀐 전체 실행에서 다음 제약을 찾는 과정**이 병렬화의 선택과 최적화입니다.
