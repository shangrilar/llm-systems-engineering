모델이 어떤 계산을 하는지, GPU가 그 계산을 어떻게 실행하는지 알았다면 이제 **그 계산을 어떤 입력으로, 어떤 순서로 반복하는지** 살펴볼 차례입니다. 같은 Transformer도 사용자의 답변을 생성할 때와 학습 데이터를 이용해 가중치를 갱신할 때 실행 모습이 달라집니다. 필요한 메모리와 좋은 성능의 기준도 함께 달라집니다.

이번 글에서는 이러한 실행 작업을 워크로드라는 관점에서 비교합니다. 먼저 입력과 반복 방식의 차이를 보고, 각 과정이 유지해야 하는 상태를 살펴보겠습니다. 이어서 요청이 도착해 응답을 마칠 때까지 추론 엔진이 담당하는 전체 흐름을 연결하겠습니다. 비교의 기준은 가중치를 고정한 표준적인 자기회귀 생성과, 알려진 토큰열로 다음 토큰을 학습하는 과정입니다.

## 워크로드를 구성하는 요소

워크로드(workload)는 단순히 모델의 이름이나 크기를 뜻하지 않습니다. **들어오는 입력, 수행할 계산, 유지할 상태, 반복 방식과 목표**를 함께 보아야 어떤 작업인지 알 수 있습니다. 같은 모델을 사용해도 한 문장에 답하는 작업과 수천 개의 문서에서 답변을 생성하는 작업은 도착 방식과 처리 목표가 다릅니다.

학습 데이터가 준비된 상황에서는 데이터를 묶어 반복적으로 처리할 수 있습니다. 반면 대화 서비스에서는 요청이 서로 다른 시점에 도착하며, 입력 길이와 실제 생성 길이도 다릅니다.

| 살펴볼 요소 | 자기회귀 생성 | Next-token 학습 |
| --- | --- | --- |
| 입력 | 프롬프트와 지금까지 선택한 출력 | 정답이 포함된 알려진 토큰열 |
| 계산 | Forward와 다음 토큰 선택 | Forward, 손실, 역전파, 가중치 갱신 |
| 반복 | 선택한 토큰으로 생성을 이어감 | 다음 데이터 배치로 학습을 이어감 |
| 주요 상태 | 요청별 토큰 이력과 재사용할 KV | 역전파에 필요한 활성값, 기울기, 옵티마이저 상태 |
| 실행 목표 | 응답 시간과 처리량·비용 | 학습 품질을 확보하며 주어진 자원으로 진척 |

모델은 주어진 텐서의 계산을 정의하고, 엔진은 필요한 입력과 상태를 준비해 그 계산을 반복합니다. 학습 엔진의 상세한 설계는 이후 학습 과정에서 다룹니다.

## 알려진 정답과 아직 모르는 다음 토큰

세 토큰 `p0 p1 p2`를 입력해 문장을 이어 쓴다고 해보겠습니다. [LM Head](/posts/embedding-to-lm-head/)는 각 입력 위치의 표현에서 다음 토큰을 선택할 점수인 logits를 계산합니다. 생성에서는 마지막 위치 `p2`의 logits로 새 토큰 `x0`를 선택합니다. 생성을 계속한다면 `x0`가 다음 실행의 입력이 되고, 그 결과로 `x1`을 선택합니다.

앞서 선택한 출력이 다음 입력이 되는 방식을 **자기회귀 생성**이라고 합니다. `x0`를 선택하기 전에는 이를 입력으로 하는 계산을 진행할 수 없습니다. 여러 요청을 함께 실행하더라도 한 요청 안의 생성 단계들이 순서대로 이어지는 이유입니다.

[![생성은 고정된 가중치로 forward와 토큰 선택을 반복하고, 학습은 알려진 여러 위치의 예측과 손실, 역전파, 가중치 갱신을 수행합니다.](/images/inference-and-training/01-execution.png)](/images/inference-and-training/01-execution.png)

오른쪽의 학습에서는 상황이 다릅니다. 학습 데이터에 `p0 p1 p2 p3`가 이미 있다면, 입력 `p0 p1 p2`에 대응하는 다음 토큰 정답은 `p1 p2 p3`입니다. 세 위치의 예측을 함께 계산하고 각 위치에서 정답에 얼마나 적절한 확률을 주었는지 평가할 수 있습니다. 앞 위치에서 모델이 어떤 토큰을 골랐는지 기다려야 다음 학습 입력을 알 수 있는 구조가 아닙니다. [Causal language modeling 설명](https://huggingface.co/docs/transformers/tasks/language_modeling)

**여러 위치를 함께 계산해도 미래를 보는 것은 아닙니다.** Causal mask 때문에 `p0` 위치는 `p1`이나 `p2`의 정보를 attention으로 가져오지 못합니다. 정답 `p1`은 `p0` 위치의 예측을 평가하는 데 쓰이고, `p1` 위치에서는 그 위치까지의 문맥으로 다음 토큰 `p2`를 예측합니다. 알려진 토큰열을 입력으로 사용한다는 사실과, 각 위치가 참조할 수 있는 문맥의 범위는 구별해야 합니다.

학습은 예측과 정답의 차이를 손실(loss)로 계산하고, 역전파(backward)로 가중치에 대한 기울기를 구합니다. 옵티마이저(optimizer)는 이 기울기를 이용해 가중치를 갱신합니다. 다음 학습 배치에서는 갱신한 가중치를 사용합니다. 생성에서는 이러한 가중치 갱신 없이 forward와 토큰 선택을 반복합니다. 그림의 화살표는 이 실행 순서이며, 각 단계의 시간이 같은 비율이라는 뜻은 아닙니다.

## 실행 목적에 따라 달라지는 상태

모델 계산이 끝난 뒤에도 다음 작업을 위해 보관할 정보가 있습니다. 실행 목적에 따라 이러한 **상태(state)가** 달라집니다.

학습에서는 역전파가 forward 중간값을 필요로 합니다. 이 중간값을 활성값(activation)이라고 하며, 보관하거나 필요할 때 다시 계산하는 방식으로 역전파에 제공합니다. 가중치의 기울기와, 옵티마이저가 갱신에 사용하는 누적 통계 등의 상태도 필요합니다. 정확히 무엇을 얼마나 저장하는지는 학습 방식과 옵티마이저에 따라 달라집니다.

생성에서는 가중치를 바꾸지 않는 대신 **요청의 진행 상황**을 유지합니다. 어떤 입력을 받았는지, 어떤 출력 토큰을 선택했는지, 어디까지 계산했는지, 언제 끝내야 하는지를 알아야 다음 단계를 이어갈 수 있습니다. 과거 입력 위치에서 계산한 Key와 Value를 저장한 **KV 캐시**도 그 상태의 하나입니다. 다음 토큰을 계산할 때 과거 계산의 일부를 재사용하는 역할을 하며, 자세한 원리는 다음 글에서 살펴봅니다.

KV 캐시와 학습의 활성값은 모두 모델 계산에서 나온 값이지만 저장 목적이 다릅니다. 전자는 이후 생성에서 문맥을 재사용하기 위한 것이고, 후자는 가중치를 학습하기 위한 역전파에 필요한 값입니다. ‘학습은 상태가 많고 추론은 상태가 없다’고 생각하면 요청이 길어지고 동시에 많아질 때의 추론 메모리 문제를 놓치게 됩니다.

요청 A와 B의 출력 이력은 따로 보관하면서도 동일한 모델 가중치를 사용할 수 있습니다. 이후 배치와 스케줄링에서 이 구분이 중요해집니다.

## 요청을 처리하는 추론 엔진

사용자가 입력한 문장은 곧바로 GPU의 행렬 곱이 되지 않습니다. 텍스트를 토큰으로 바꾸고, 요청의 생성 조건을 정리하고, 실행할 기회를 기다려야 합니다. 실행 뒤에는 결과를 요청별로 되돌리고, 출력을 전달하며, 끝난 요청의 자원을 정리해야 합니다. **추론 엔진은 이 과정들을 모델 실행과 연결합니다.** 실제 시스템은 입력 처리·엔진·모델 실행을 여러 구성 요소로 나눌 수 있습니다. [vLLM의 구조 설명](https://docs.vllm.ai/en/latest/design/arch_overview/)

[![요청은 입력 준비와 대기를 거쳐 자원에 맞게 선택되어 실행되고 상태와 출력을 갱신합니다. 미완료 요청은 반복하고 KV 부족 시 진입 지연이나 중단과 회수로 처리합니다.](/images/inference-and-training/02-request-lifecycle.png)](/images/inference-and-training/02-request-lifecycle.png)

새 요청은 입력 준비 후 대기 큐에 들어갑니다. 엔진은 진행 중인 요청과 새 요청 중 이번 실행에 포함할 작업을 선택합니다. 여러 요청의 작업을 묶어 실행하는 단위를 **배치(batch)라고** 하고, 실행 대상을 고르는 일을 **스케줄링(scheduling)이라고** 합니다.

선택할 때는 이번 실행에서 처리할 토큰 수와 KV 저장 공간을 함께 고려합니다. 계산을 많이 넣으면 한 단계가 길어지고, 저장 공간이 없으면 계산 결과를 유지할 수 없습니다. 선택과 자원 확보가 서로 맞춰지는 과정입니다.

모델을 실행하면 새로 계산한 KV와 선택한 출력 토큰을 요청 상태에 반영합니다. 출력을 사용자에게 전달하고, 아직 끝나지 않은 요청은 다음 단계의 선택 대상으로 돌아갑니다. 완료되거나 취소된 요청은 더 이상 필요하지 않은 자원을 반환합니다. 출력 전달과 다음 계산이 겹칠 수도 있으므로 그림은 특정 엔진의 함수 호출 순서를 그대로 나타낸 것은 아닙니다.

여기서 **진행 중인 모든 요청이 매번 같은 배치에 들어가는 것은 아닙니다.** 이번 단계에 처리할 토큰 수를 제한하느라 일부 요청이 쉬더라도 그 요청의 KV는 남겨둘 수 있습니다. KV 공간이 부족한 경우에는 새 요청의 진입을 늦추거나, 진행 중인 요청을 중단하고 실제 KV 공간을 회수하는 선택이 필요할 수 있습니다. 배치에서 빼는 동작과 저장 공간을 반환하는 동작은 별개입니다. 이러한 중단·회수·재개는 뒤에서 자세히 살펴보며, 여기서는 모델 실행 단계 사이의 요청 관리라는 점만 기억하면 됩니다.

## 요청마다 다른 길이와 성능 목표

요청 A는 짧은 답변을 원하고, B는 긴 문서를 작성하며, 두 요청이 진행되는 동안 C가 도착한다고 해보겠습니다. 엔진은 A가 먼저 끝난 자리를 어떻게 사용할지, B가 문맥을 얼마나 더 저장할지, C를 언제 시작할지 판단해야 합니다. 실제 출력 길이는 종료할 때까지 확정되지 않을 수 있어, 처음 한 번의 결정으로 모든 실행을 정하기 어렵습니다.

목표도 하나가 아닙니다. 대화 서비스에서는 첫 응답이 빨리 나오는지와, 이후 응답이 얼마나 꾸준히 이어지는지가 모두 중요합니다. 반면 많은 문서를 미리 처리하는 작업에서는 전체 작업량을 일정 시간과 비용 안에 끝내는 것이 더 중요할 수 있습니다. 함께 실행할 요청을 늘려 서버의 처리량이 좋아져도 각 사용자의 대기 시간이 같은 비율로 줄어드는 것은 아닙니다. 응답 시간 제약과 처리량을 함께 보는 이유입니다. [DistServe의 성능 목표](https://arxiv.org/abs/2401.09670)

학습에서도 학습 품질을 유지하면서 같은 자원으로 얼마나 진척하는지가 중요합니다. 다만 이를 ‘학습은 언제나 계산 병목, 추론은 언제나 메모리 병목’으로 단순화하지는 않겠습니다. 생성 안에서도 입력 문맥을 처리하는 때와 새 토큰을 하나씩 이어가는 때의 계산 형태가 다르기 때문입니다. 이 차이는 [Prefill과 Decode](/posts/prefill-and-decode/)에서 다룹니다.

SFT도 통상 post-training에 포함되지만, 이 사이트는 교육 순서에 따라 Pretraining·SFT를 학습 단계에서, RL 기반 post-training을 그다음에 다룹니다. RL 기반 과정에서는 생성한 결과를 학습에 사용하는 등 두 실행이 연결됩니다.

이제 요청 전체의 지도를 보았으니 그 안의 반복을 확대해 보겠습니다. [추론과 KV 캐시](/posts/inference-kv-cache/)에서는 한 토큰을 선택한 뒤 다음 토큰을 계산할 때, 무엇을 다시 계산하고 무엇을 재사용하는지 따라가겠습니다.
