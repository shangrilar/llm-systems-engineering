[KV 캐시 관리와 PagedAttention](/posts/paged-kv-cache/)에서는 요청의 캐시를 작은 블록으로 나누어 필요할 때 배정하고 종료 후 반환했습니다. 하지만 모든 블록을 사용 중인데 진행 중인 요청이 더 긴 출력을 만들려 한다면, 주소를 유연하게 관리하는 것만으로는 새 공간이 생기지 않습니다.

이 글에서는 실행을 잠시 미루는 것과 저장 공간을 회수하는 것을 구별하겠습니다. 이어서 진행 중인 요청의 KV를 회수한 뒤, 이미 생성한 토큰 이력을 보존하면서 계산 상태를 다시 만들어 재개하는 과정을 보겠습니다. 마지막에는 재계산과 다른 저장소로의 이동이 각각 어떤 비용을 만드는지 살펴보겠습니다.

## 시작할 수 있었어도 계속 늘어날 수 있다

요청을 처음 받아들일 때 입력 문맥의 KV가 들어갈 공간이 있다고 해도, 그 요청이 종료될 때까지 필요한 공간이 모두 확보됐다는 뜻은 아닙니다. 일반적인 생성에서는 다음 토큰이 선택되고 다시 입력될 때마다 KV에 새 위치가 추가됩니다. 출력이 얼마나 길어질지도 미리 정확히 알기 어렵습니다.

최대 출력 길이 전체를 미리 예약하면 이런 상황을 줄일 수 있지만, 실제로 짧게 끝나는 요청의 공간을 오래 잡아 둘 수 있습니다. 반대로 필요한 만큼만 배정하면 공간을 더 유연하게 사용하지만, 나중에 추가 공간을 요청할 때 부족해질 수 있습니다. 엔진은 수용할 요청 수와 진척 중인 요청들의 자원을 함께 관리해야 합니다.

신규 요청 C의 공간이 부족하다면 C를 대기시키는 선택이 있습니다. 이는 아직 시작하지 않은 요청의 진입을 늦추는 것입니다. 그러나 A와 B가 이미 실행 중이고 A의 다음 위치를 저장할 블록이 없다면, 대기 큐에 있는 C를 계속 기다리게 하는 것만으로 현재 문제를 해결하지 못할 수 있습니다.

## 배치에서 빼는 것과 KV를 회수하는 것

앞선 글과 다른 용량 조건으로, 물리 블록이 네 개뿐인 작은 예시를 만들겠습니다. A와 B가 두 개씩 독점하고 있고 빈 블록은 없습니다. A가 다음 입력을 처리하려면 블록 하나가 더 필요합니다. 여기서는 B를 중단 대상으로 선택한다고 가정합니다. 어느 요청을 고르는 것이 최적인지에 대한 예시는 아닙니다.

[![B를 이번 배치에서 빼도 KV를 유지하면 빈 블록은 없지만, B의 두 KV 블록을 반환하면 A에 새 블록 하나를 배정할 수 있습니다.](/images/inference-preemption/01-reclaim-kv.png)](/images/inference-preemption/01-reclaim-kv.png)

B를 이번 실행에서 제외해도 GPU KV를 그대로 두면 블록 풀은 여전히 `[A, A, B, B]`입니다. 이번 단계에 처리할 토큰 수는 줄었지만 저장 공간은 늘지 않았습니다. 실행 토큰 예산 부족 때문에 B를 쉬게 할 때는 충분할 수 있어도, A의 새 KV 공간을 마련하지는 못합니다.

B의 KV 블록 두 개를 실제로 반환하면 풀은 `[A, A, 빈칸, 빈칸]`이 됩니다. 그중 하나를 A에 배정해 `[A, A, A, 빈칸]`으로 만들 수 있습니다. B는 끝난 요청이 아니라 **재개할 계산 상태를 복구해야 하는 요청**으로 남습니다.

이처럼 다른 요청이 진행할 수 있도록 실행 중인 요청의 자원을 회수하는 선택을 여기서는 **preemption(선점)이라고** 부릅니다. 이 글의 범위는 KV 압박에 따른 요청 관리이며, 보통 모델 실행 단계 사이에서 판단합니다. GPU에서 이미 실행 중인 커널을 강제로 중단하는 기능을 설명하는 것이 아닙니다.

## 토큰 이력을 남기고 계산 상태를 다시 만들기

KV를 버리면 지금까지 생성한 문장도 사라질까요? 입력과 출력 토큰 ID의 이력을 별도로 유지하면 그렇지 않습니다. 토큰 이력은 어떤 위치에 어떤 토큰이 있었는지를 나타내고, KV는 그 이력을 모델로 계산해 얻은 레이어별 상태입니다. 둘은 다른 데이터입니다.

앞선 공간 회수 예시와 별도로 B의 토큰 경계만 확대해 보겠습니다. 입력 p0·p1·p2를 처리해 x0를 선택하고, x0를 다시 입력해 x1까지 선택·전달한 상태입니다. 중단 직전의 이력은 `p0 p1 p2 x0 x1`이지만, 계산된 KV는 `p0 p1 p2 x0`까지입니다. x1은 다음 실행에 들어갈 토큰이므로 아직 자기 KV가 없습니다.

[![중단 전 이력 p0·p1·p2·x0·x1을 보존하고 GPU KV를 해제합니다. 재개할 때 이 고정 이력을 계산해 KV를 복구하고 새 출력 x2만 선택·전달합니다.](/images/inference-preemption/02-recompute-resume.png)](/images/inference-preemption/02-recompute-resume.png)

**Recompute(재계산)** 방식은 GPU KV를 반환한 뒤, 다시 공간을 얻었을 때 보존한 이력을 입력으로 계산합니다. 그림에서는 `p0 p1 p2 x0 x1` 전체를 알려진 토큰열로 처리합니다. 그 결과 x1까지의 KV가 만들어지고, 마지막 위치의 logits에서 새로운 x2를 선택할 수 있습니다. Prefix 재사용이 없는 이 예시는 전체를 다시 계산하지만, 실제 복구 범위는 남아 있는 캐시와 엔진 방식에 따라 달라질 수 있습니다.

이때 x0와 x1을 다시 샘플링하지 않습니다. 이미 결정된 입력 이력으로 사용합니다. 사용자에게 x0·x1을 다시 보내지도 않고 새 x2부터 이어 전달합니다. 원래의 대답을 처음부터 새로 만드는 것과, 그 대답에 필요한 계산 상태를 다시 만드는 것은 다릅니다.

엔진은 토큰 이력 외에도 요청의 생성 설정, 위치, 진행 상태와 이미 전달한 출력의 경계를 유지해야 합니다. 재개 과정의 forward가 여러 위치를 처리하더라도 복구한 과거 위치들을 새 출력처럼 집계해서는 안 됩니다. [PagedAttention 논문](https://arxiv.org/html/2309.06180v1)의 preemption 설명과 [vLLM의 운영 문서](https://docs.vllm.ai/en/latest/configuration/optimization/#preemption)는 공간 부족 시 요청을 중단하고 계산 상태를 재구성하는 사례를 보여줍니다.

## 재계산과 이동의 비용

KV를 GPU 밖의 저장 공간에 옮겨 두었다가 다시 가져오는 **swap**도 생각할 수 있습니다. 이 경우 값 자체를 보관하므로 재개할 때 과거 전체를 같은 방식으로 재계산할 필요가 없습니다. 대신 KV를 내보내고 가져오는 전송 시간과 CPU 메모리 같은 별도 저장 공간이 필요합니다.

| 방식 | 중단 시 보존하는 것 | 재개에 필요한 주요 작업 |
| --- | --- | --- |
| Recompute | 토큰 이력과 요청 상태 | 필요한 이력을 계산해 KV 재구성 |
| Swap | 요청 상태와 다른 저장소의 KV | KV를 다시 GPU로 전송하고 다음 계산 준비 |

이 표는 개념 비교입니다. 모든 엔진이 두 방식을 함께 제공하거나 같은 기준으로 선택한다는 뜻은 아닙니다. 현재 구현에 특정 방식을 적용하려면 해당 버전의 지원 범위와 설정을 확인해야 합니다.

어느 쪽이 더 싼지도 조건에 달려 있습니다. 재계산 시간은 복구할 토큰 수와 모델 실행 효율의 영향을 받습니다. 이동 시간은 KV 데이터량과 사용 가능한 전송 대역폭, 다른 전송과의 경쟁에 영향받습니다. 문맥이 길어지면 두 비용 모두 커질 수 있지만 같은 비율로 변한다고 가정할 수는 없습니다.

또한 KV를 이동하려면 전송이 안전하게 끝나야 그 GPU 공간을 다른 요청에 재사용할 수 있습니다. 배치에서 제외했다는 상태 표시 하나만으로 메모리가 즉시 비는 것은 아니라는 원칙은 swap에도 적용됩니다.

## 진행을 가능하게 하지만 대기를 만든다

Preemption은 공간이 부족한 상황에서 일부 요청이 계속 진행할 수 있게 합니다. 동시에 중단된 요청은 기다리고 복구하는 비용을 부담합니다. 이미 첫 출력을 받은 뒤 중단됐다면 다음 출력까지 긴 간격이 생길 수 있고, 첫 출력 전이라면 첫 응답이 늦어질 수 있습니다.

요청을 많이 받아들인 뒤 계속 중단·재계산하면 같은 이력을 반복해서 계산하느라 새 출력의 진척이 줄어들 수 있습니다. 그래서 preemption 횟수만 보거나 동시 요청 수만 높이는 것으로 운영이 개선됐다고 판단하기 어렵습니다. 대기 중인 요청, 실제 새 출력의 처리량, 지연 분포를 함께 보아야 합니다.

이 현상은 요청 진입 정책, 배치 제한과 KV 예산을 다시 살펴볼 근거가 됩니다. 복잡한 우선순위·공정성 정책은 후속 주제로 남기고, 먼저 [추론 성능 지표: 대기 시간과 처리량](/posts/inference-metrics/)에서 대기와 복구가 사용자 관측 시간에 어떻게 나타나는지 살펴보겠습니다.
