[The previous article](/en/posts/model-advanced-sparse-indexer/) used an indexer to choose KV positions to read. This time, we will examine <strong>how information from several token positions is combined into a single summary KV entry before selection</strong>. Reading entries that represent several positions, rather than one entry per position, lets us handle a long context with fewer entries.

We will first distinguish the compression axis from the one we learned about in MLA. Then we will trace the calculation that turns two input positions into one summary vector, examine why completed summaries are read alongside recent per-token KV, and finally connect compression to selecting summaries with an indexer.

## Vector width and the number of token positions

Saying that KV storage shrinks does not tell us what becomes smaller. When per-position vectors are stacked as rows, reducing the number of components in each row and combining several rows into one are different changes.

Both sides of Figure 1 start with eight rows and four components. Rows denote token positions <math aria-label="p0"><msub><mi>p</mi><mn>0</mn></msub></math> through <math aria-label="p7"><msub><mi>p</mi><mn>7</mn></msub></math>, and columns denote vector components. The grid does not represent the number of heads.

<a href="/images/model-advanced-token-compression/en/01-compression-axes.png?v=0aa059d54037" id="figure-1"><picture><source width="720" height="3608" media="(max-width: 600px)" srcSet="/images/model-advanced-token-compression/en/01-compression-axes-mobile.png?v=1556897f65c7" /><img width="2400" height="3014" src="/images/model-advanced-token-compression/en/01-compression-axes.png?v=0aa059d54037" alt="Both panels begin with eight positions and four components. The left preserves eight positions while reducing each vector to two components. The right combines adjacent pairs into four summaries, each with four components." loading="lazy" /></picture></a>

On the left, each position's representation shrinks from four components to two. There are still eight positions, so the result has eight rows and two components. The latent representation in [MLA's storage structure](/en/posts/model-advanced-mla-storage/) can also be understood as reducing the width of the vector stored at each position. Actual MLA also has separate positional components, however, so this grid does not represent its entire cache size.

On the right, two adjacent positions form one summary. Positions <math aria-label="p0"><msub><mi>p</mi><mn>0</mn></msub></math> and <math aria-label="p1"><msub><mi>p</mi><mn>1</mn></msub></math> become <math aria-label="b0"><msub><mi>b</mi><mn>0</mn></msub></math>, while <math aria-label="p2"><msub><mi>p</mi><mn>2</mn></msub></math> and <math aria-label="p3"><msub><mi>p</mi><mn>3</mn></msub></math> become <math aria-label="b1"><msub><mi>b</mi><mn>1</mn></msub></math>. Each summary retains four components, while the number of entries falls from eight to four, giving four rows and four components. This is the <strong>token-axis compression</strong> covered in this article. Reducing the token count here means reducing the number of KV entries attention reads, not the number of output tokens the model generates.

Summary <math aria-label="b0"><msub><mi>b</mi><mn>0</mn></msub></math> is not simply the original KV at <math aria-label="p0"><msub><mi>p</mi><mn>0</mn></msub></math> left in place. It is a new representation that combines information from two positions. This also distinguishes compression from an indexer that selects positions: an indexer chooses some candidates, whereas compression combines information from several candidates into a new entry. The two final grids have the same number of cells, but that does not mean they contain the same information or involve the same computation.

## Building a summary vector with two projections

We could simply average every component across two positions. Here, instead, we examine <strong>a learned way to determine how much each position contributes to each component</strong>. The same input feeds two paths. The content projection creates vectors to include in the summary, and the score projection creates scores used to determine how to mix that content.

The inputs in Figure 2 are the vectors <math aria-label="h0"><msub><mi>h</mi><mn>0</mn></msub></math> = [1, 0] and <math aria-label="h1"><msub><mi>h</mi><mn>1</mn></msub></math> = [0, 1] at two positions. Let H be the matrix that stacks them as rows. This example combines two positions into one while retaining two components.

<a href="/images/model-advanced-token-compression/en/02-weighted-summary.png?v=47974218ab23" id="figure-2"><picture><source width="720" height="3802" media="(max-width: 600px)" srcSet="/images/model-advanced-token-compression/en/02-weighted-summary-mobile.png?v=c1c43b186567" /><img width="2400" height="3052" src="/images/model-advanced-token-compression/en/02-weighted-summary.png?v=47974218ab23" alt="Input H=[[1,0],[0,1]] is projected with content matrix Wu=[[2,0],[0,4]] and score matrix Ws=[[ln3,0],[0,ln3]]. Position-wise softmax produces A=[[.75,.25],[.25,.75]]. Elementwise multiplication with U followed by summation across positions yields c0=[1.5,3]. All values are educational examples." loading="lazy" /></picture></a>

The first step multiplies H by two different projection matrices, <math aria-label="Wu"><msub><mi>W</mi><mi>u</mi></msub></math> and <math aria-label="Ws"><msub><mi>W</mi><mi>s</mi></msub></math>. These are learned parameters: <math aria-label="Wu"><msub><mi>W</mi><mi>u</mi></msub></math> produces content vectors, and <math aria-label="Ws"><msub><mi>W</mi><mi>s</mi></msub></math> produces per-component scores. <strong>The model learns the projection matrices; the projection outputs depend on the input.</strong> The matrix values in the figure are educational examples chosen to make the arithmetic easy to follow.

The two rows of the content projection <math aria-label="Wu"><msub><mi>W</mi><mi>u</mi></msub></math> are [2, 0] and [0, 4]. Multiplying <math aria-label="h0"><msub><mi>h</mi><mn>0</mn></msub></math> by this matrix gives [2, 0], and multiplying <math aria-label="h1"><msub><mi>h</mi><mn>1</mn></msub></math> gives [0, 4]. Stacking those results as rows gives the content matrix U. No positions have been combined yet: the content at each position has only been transformed.

The two rows of the score projection <math aria-label="Ws"><msub><mi>W</mi><mi>s</mi></msub></math> are [ln 3, 0] and [0, ln 3]. Multiplying the same input H by this matrix gives a score matrix S with those same values. The projection matrix and its output look identical here because we chose the identity matrix as the input; this is not true for a general input. <strong>The values ln 3 and 0 are not calculated from the content vector [2, 0]. They come from projecting the same input with a separate score matrix.</strong>

These scores are not used directly as weights. For each component, softmax is applied across the two positions. This normalizes each column vertically in the figure. For the first component, the scores [ln 3, 0] exponentiate to [3, 1]. Dividing by their sum, 4, gives [0.75, 0.25]. For the second component, the scores [0, ln 3] give weights [0.25, 0.75]. We chose ln 3 and 0 to obtain these simple proportions.

Each column of the resulting weight matrix A sums to 1. The first component takes 75% from position 0 and 25% from position 1; the second component does the reverse. The mixing proportions are set separately for each component, rather than applying one pair of proportions to the entire vector.

The second step <strong>multiplies corresponding components of U and A, then sums across positions</strong>. Unlike the earlier projection, this is elementwise multiplication, not matrix multiplication. The first component is 2 × 0.75 + 0 × 0.25 = 1.5, and the second is 0 × 0.25 + 4 × 0.75 = 3. The final summary <math aria-label="c0"><msub><mi>c</mi><mn>0</mn></msub></math> is [1.5, 3]. Two per-position entries have become one summary while retaining two components.

These weights have a different role from the weights obtained by comparing the current query and keys in main attention. <strong>Compression weights build a summary; attention weights read the completed summaries.</strong> The current query does not participate in summary creation in Figure 2. Completed summaries can be cached and reused by later queries.

The [Compressor in DeepSeek-V4's official implementation](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/inference/model.py) likewise applies content and score projections to the same input, then compresses with a softmax and weighted sum over positions. The figure isolates that calculation in a small example. It omits the implementation's positional bias, overlapping compression ranges, subsequent normalization, and positional processing. It does not mean that combining arbitrary existing KV entries this way preserves the original attention output exactly.

## Completed summaries and recent per-token KV

To combine positions, their inputs must all have arrived. When processing tokens one at a time, some groups remain incomplete. At the same time, recent context can be retained as individual positions instead of relying entirely on summaries.

Figure 3 creates one summary for every two positions and separately retains KV for the latest three positions, including the current one. We will call this <strong>recent per-token KV</strong>. It means KV entries that have not been combined across positions, not the input vectors entering the model. “Original” in the figure likewise refers to entries before token-axis compression.

<a href="/images/model-advanced-token-compression/en/03-causal-summary-and-local.png?v=7536c32c9645" id="figure-3"><picture><source width="720" height="3676" media="(max-width: 600px)" srcSet="/images/model-advanced-token-compression/en/03-causal-summary-and-local-mobile.png?v=5d3150bb0252" /><img width="2400" height="3116" src="/images/model-advanced-token-compression/en/03-causal-summary-and-local.png?v=7536c32c9645" alt="At p6, summaries b0 through b2 are complete, while b3 includes future p7 and cannot be read. Query q6 reads completed summaries and recent per-token KV at positions 4,5,6. At p8, b3 is also complete, and recent per-token KV covers 6,7,8. Future p9 is excluded." loading="lazy" /></picture></a>

When processing <math aria-label="p6"><msub><mi>p</mi><mn>6</mn></msub></math>, summaries <math aria-label="b0"><msub><mi>b</mi><mn>0</mn></msub></math> for <math aria-label="p0"><msub><mi>p</mi><mn>0</mn></msub></math> and <math aria-label="p1"><msub><mi>p</mi><mn>1</mn></msub></math>, <math aria-label="b1"><msub><mi>b</mi><mn>1</mn></msub></math> for <math aria-label="p2"><msub><mi>p</mi><mn>2</mn></msub></math> and <math aria-label="p3"><msub><mi>p</mi><mn>3</mn></msub></math>, and <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math> for <math aria-label="p4"><msub><mi>p</mi><mn>4</mn></msub></math> and <math aria-label="p5"><msub><mi>p</mi><mn>5</mn></msub></math> are complete. But group <math aria-label="b3"><msub><mi>b</mi><mn>3</mn></msub></math>, which combines <math aria-label="p6"><msub><mi>p</mi><mn>6</mn></msub></math> and <math aria-label="p7"><msub><mi>p</mi><mn>7</mn></msub></math>, cannot yet be completed. If <math aria-label="q6"><msub><mi>q</mi><mn>6</mn></msub></math> read a summary containing future position <math aria-label="p7"><msub><mi>p</mi><mn>7</mn></msub></math>, it would be using future information.

Thus, <math aria-label="q6"><msub><mi>q</mi><mn>6</mn></msub></math> reads completed summaries <math aria-label="b0"><msub><mi>b</mi><mn>0</mn></msub></math>, <math aria-label="b1"><msub><mi>b</mi><mn>1</mn></msub></math>, and <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math> alongside recent per-token KV at <math aria-label="p4"><msub><mi>p</mi><mn>4</mn></msub></math>, <math aria-label="p5"><msub><mi>p</mi><mn>5</mn></msub></math>, and <math aria-label="p6"><msub><mi>p</mi><mn>6</mn></msub></math>. The “Summary bank” in the figure is the cache of completed summaries. We temporarily leave selection aside and assume all completed summaries are read. Information at the current position <math aria-label="p6"><msub><mi>p</mi><mn>6</mn></msub></math>, which is not yet part of a summary, is available through recent per-token KV.

Why retain individual KV for <math aria-label="p4"><msub><mi>p</mi><mn>4</mn></msub></math> and <math aria-label="p5"><msub><mi>p</mi><mn>5</mn></msub></math> when they have already been combined into <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math>? Summary <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math> is a single entry mixing two positions. A query can assign a weight to <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math>, but it cannot separate <math aria-label="p4"><msub><mi>p</mi><mn>4</mn></msub></math> and <math aria-label="p5"><msub><mi>p</mi><mn>5</mn></msub></math> within it and assign different attention weights to each. <strong>Keeping recent per-token KV lets attention distinguish and read nearby positions individually.</strong>

Summary creation and recent KV retention follow separate rules. A summary is added when its group is complete, while individual KV remains as long as it is within the window. Compression therefore does not immediately delete individual KV for those positions. Summary <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math> and positions <math aria-label="p4"><msub><mi>p</mi><mn>4</mn></msub></math> and <math aria-label="p5"><msub><mi>p</mi><mn>5</mn></msub></math> contain information from the same period, but they are different read entries. This differs from the previous article's case where a window and an indexer selected the same original position and the duplicate was removed.

On the right, processing has reached <math aria-label="p8"><msub><mi>p</mi><mn>8</mn></msub></math>, so summary <math aria-label="b3"><msub><mi>b</mi><mn>3</mn></msub></math> for <math aria-label="p6"><msub><mi>p</mi><mn>6</mn></msub></math> and <math aria-label="p7"><msub><mi>p</mi><mn>7</mn></msub></math> is also complete. Recent per-token KV now covers <math aria-label="p6"><msub><mi>p</mi><mn>6</mn></msub></math>, <math aria-label="p7"><msub><mi>p</mi><mn>7</mn></msub></math>, and <math aria-label="p8"><msub><mi>p</mi><mn>8</mn></msub></math>. Positions <math aria-label="p4"><msub><mi>p</mi><mn>4</mn></msub></math> and <math aria-label="p5"><msub><mi>p</mi><mn>5</mn></msub></math> have left the recent window, so their individual KV is removed from this path, while their information remains summarized in <math aria-label="b2"><msub><mi>b</mi><mn>2</mn></msub></math>. Summary <math aria-label="b4"><msub><mi>b</mi><mn>4</mn></msub></math>, which would include the still-future position <math aria-label="p9"><msub><mi>p</mi><mn>9</mn></msub></math>, is not read.

Summarizing every two positions does not make this cache fixed in size. Recent per-token KV stays at three entries, but one past summary is added for every two input positions. There is also intermediate state needed while building summaries. Token-axis compression slows the growth in the number of entries storing past information; it does not turn an entire long context into a single fixed-size state.

## Combining compression and an indexer

As summaries accumulate, we can choose to read only some of them. Whereas the previous article's indexer selected token positions, it now <strong>selects compressed summary entries</strong>. Another design is to create sufficiently few summaries and read them all.

Figure 4 shows two paths for handling completed past positions <math aria-label="p0"><msub><mi>p</mi><mn>0</mn></msub></math> through <math aria-label="p15"><msub><mi>p</mi><mn>15</mn></msub></math> at the current position <math aria-label="p16"><msub><mi>p</mi><mn>16</mn></msub></math>. Both also read recent per-token KV at <math aria-label="p14"><msub><mi>p</mi><mn>14</mn></msub></math>, <math aria-label="p15"><msub><mi>p</mi><mn>15</mn></msub></math>, and <math aria-label="p16"><msub><mi>p</mi><mn>16</mn></msub></math>. What changes is the group size for past positions and how summaries are selected.

<a href="/images/model-advanced-token-compression/en/04-compress-and-select.png?v=c75c873a2cd1" id="figure-4"><picture><source width="720" height="4054" media="(max-width: 600px)" srcSet="/images/model-advanced-token-compression/en/04-compress-and-select-mobile.png?v=3f5701432150" /><img width="2400" height="3254" src="/images/model-advanced-token-compression/en/04-compress-and-select.png?v=c75c873a2cd1" alt="The left groups positions 0 through 15 in pairs, stores eight summaries, and selects b1 and b5. The right groups the same positions in fours and reads all four summaries. Both read recent per-token KV at positions 14,15,16." loading="lazy" /></picture></a>

On the left, groups of two positions produce eight summaries. The indexer selects the Top-2 entries, <math aria-label="b1"><msub><mi>b</mi><mn>1</mn></msub></math> and <math aria-label="b5"><msub><mi>b</mi><mn>5</mn></msub></math>. Summary <math aria-label="b1"><msub><mi>b</mi><mn>1</mn></msub></math> represents positions 2 and 3, and <math aria-label="b5"><msub><mi>b</mi><mn>5</mn></msub></math> represents positions 10 and 11. After selection, attention does not expand these back into the four original positions' KV: <strong>it reads the two selected summaries themselves</strong>. Including the three recent per-token KV entries gives five read entries in this example.

On the right, groups of four positions produce four summaries, all of which are read. Adding the same three recent per-token KV entries gives seven read entries. Despite stronger compression, this example reads more entries than the left-hand path, because the left-hand path has a separate selection step. <strong>How many entries compression stores and how many of them attention reads must be distinguished.</strong>

The left-hand path does not retain only the two summaries being read now. It keeps eight summaries as candidates because the next query may select different ones. The right-hand path stores four summaries and reads them all. This educational example distinguishes storage from reading; it is not a performance comparison establishing that reading five entries must be faster than reading seven. The left-hand path also pays for indexer scoring and selection.

[DeepSeek-V4's official attention implementation](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/inference/model.py) combines compressed-entry indices with positions in the recent window. The groups of two and four in the figure do not reproduce the actual model's compression ratios. The relationship to learn here is the distinction between selecting some compressed entries and reading all of a smaller set of summaries.

Larger groups yield fewer summaries, but each vector must hold information from more positions. An indexer cannot recover details that have already become difficult to distinguish during compression. The compression level, number of selected entries, and recent per-token KV window size therefore need to be chosen together. This trades the benefit of storing and reading fewer entries against how much useful information is retained.
