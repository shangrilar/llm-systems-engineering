One of the main costs of long-context inference is the **KV cache**: the Keys and Values of earlier positions, stored so they do not have to be recomputed every time a new token is generated. As the [KV cache article](/en/posts/inference-kv-cache/) showed, this storage grows in proportion to context length and is multiplied by the number of requests served at once. So how much the cache grows when the context gains one token goes a long way toward setting the cost of long-context inference.

DeepSeek changed its attention design several times between V2 and V4.1. This article follows those changes through one number, the **KV cache per token**. A hypothetical MHA model with V2's dimensions, storing every head's Key and Value, would use about 3.9 MB per token. V4.1-Flash uses 890 B per token (the growth per token in a long context; the local KV that keeps recent positions is separate), about 1/4,400 of that.

This reduction did not happen in a single step. The cache per token can be seen roughly as built from four factors.

```text
KV cache per token ≈ width of the stored vector (dimensions)
                     × number of layers storing KV
                     × bytes per element
                     ÷ compression ratio (how many tokens' KV is merged into one)
```

V2's MLA narrowed the **width of the stored vector**. V3.2's DSA reduced **the number of positions read**, rather than the amount stored. V4's CSA and HCA use **compression along tokens**, merging the KV of several tokens into one stored vector, and V4.1's CSA2 lets layers share KV to reduce the **number of layers that store KV for the whole context**. Along the way, bytes per element also dropped from BF16 (2 B) to FP8 (1 B) and then FP4 (0.5 B). Below, we look at what changed in each generation through figures and then work out the numbers ourselves.

<details>
<summary>More detail: how this article counts "KV cache per token"</summary>

- **Average growth in a long context.** Compressed models need 4 or 128 tokens before one compressed KV appears, so the same amount is not added at every token. We take the total cache (without the local KV below) divided by the number of tokens once the context is long enough.
- **One copy of the model body, one request.** When several requests run at once, each keeps its own cache, so multiply by the number of requests. Storage per GPU has to be worked out separately, depending on whether tensor parallelism splits or replicates the cache. The MTP module (an auxiliary module that predicts several next tokens together) is excluded.
- **Search keys are included.** A search key is the small key an indexer scores to rank candidate positions; the flow diagrams label it "indexer key." From V3.2 on, models store these keys separately to pick positions to read. They also build up in proportion to context, so they are counted.
- **The local KV cache that keeps only recent positions is listed separately.** Once the last 128 positions are filled it stops growing, so it is not part of the per-token growth. The local KV values in the figure are the data size of the last 128 positions, excluding intermediate compression state.
- **These values are computed from model configs and cache formats, not measured on GPUs.**
- **The hypothetical MHA** is a reference that assumes the same size as V2 (60 layers, 128 heads, 128 dimensions per head) with every head's Key and Value stored. No such model exists, and it is not meant to be an MHA model of equal quality.

</details>

## The baseline: MHA that stores every head's Key and Value

The starting point is [core attention](/en/posts/core-attention/). In MHA, each layer builds a Key and a Value for every head and stores both in the cache. Plugging in V2's numbers, storing one token takes:

```text
Hypothetical MHA: 60 layers × 128 heads × (Key 128 + Value 128) × 2 B (BF16)
                = 3,932,160 B ≈ 3.9 MB
```

At about 3.9 MB per token, a 128K-token context (131,072 positions) needs about 515 GB of cache for a single request. In decode, this whole cache is read for every new token. Storage and reads are both a problem. [MQA and GQA](/en/posts/model-advanced-mqa-gqa/) cut this value by letting several heads share Key and Value. DeepSeek took a different path.

## DeepSeek-V2

V2 narrows the **width of the stored vector** with **MLA** (Multi-head Latent Attention). Instead of per-head Key and Value, it stores a small shared vector (the latent) from which they can be built, plus a positional Key. The model does not compress MHA's Key and Value and restore them; it is trained from the start with Key and Value built from the latent. Below we look at what is stored, how attention is computed without expanding per-head Key and Value (rebuilding them from the cache), and then the storage per token. Figure 2 shows the effect.

### MLA: three paths from the same input

Before the figures, a word on notation. In this article's matrix figures, activations have tokens as rows and features as columns, and weights have the shape [input, output]. Box widths show only the order of column sizes and are not to scale. Purple boxes are learned weights W, and the superscript of W says what the weight does.

| Notation | Meaning | Examples |
| --- | --- | --- |
| D | down-projection: shrinks to a small latent | W<sup>DQ</sup>: X → C<sup>Q</sup>, W<sup>DKV</sup>: X → C<sup>KV</sup> |
| U | up-projection: rebuilds per-head values from a latent | W<sup>UQ</sup>: C<sup>Q</sup> → per-head Query, W<sup>UK</sup>, W<sup>UV</sup>: C<sup>KV</sup> → per-head Key, Value |
| Q, K, V, O | what is produced: Query, Key, Value, Output | W<sup>O</sup>: output projection |
| R | the positional part that RoPE rotates | W<sup>QR</sup>, W<sup>KR</sup>, Q<sup>R</sup><sub>h</sub>, K<sup>R</sup> |
| C | as a letter, C<sup>Q</sup> and C<sup>KV</sup> are compressed latents; as a superscript (Q<sup>C</sup><sub>h</sub>, K<sup>C</sup><sub>h</sub>), the content part | |
| subscript h | the value for head h; each head has its own | Q<sup>C</sup><sub>h</sub>, W<sup>UK</sup><sub>h</sub> |
| T, D, H | number of tokens, width of the input X (hidden size), number of heads | X: [T, D] |
| d<sub>k</sub>, d<sub>v</sub>, d<sub>r</sub>, r<sub>q</sub>, r<sub>kv</sub> | per-head Key content width, Value width, positional width, Query latent width, KV latent width | |
| A, B, B<sup>T</sup> | marks beside a product: of the two operands, A comes first and B second. B<sup>T</sup> means B is transposed before multiplying | |

The figures draw all T tokens of the context computed at once. When decode produces one new token, the Query side is only the last row, while the Key and Value side is all T cached positions.

Figure 3 shows how the input X branches into three paths within an MLA layer: one for the queries, one for the shared KV latent, and one for the positional key. Each path is drawn starting again from the same input X.

<AnnotPart fig="mla-flow/01-projections" panels="1">

**Query path.** X is reduced to a Query latent C<sup>Q</sup> (1,536 dimensions), and from it each head builds a content query Q<sup>C</sup><sub>h</sub> and a positional query Q<sup>R</sup><sub>h</sub>. Queries are not stored in the KV cache for later tokens.

</AnnotPart>
<AnnotPart fig="mla-flow/01-projections" panels="2">

**Shared KV path.** X is reduced to the 512-dimensional C<sup>KV</sup>, which is **stored in the cache**. Per-head Keys and Values are not stored, because they can be built by multiplying C<sup>KV</sup> by per-head weights W<sup>UK</sup><sub>h</sub> and W<sup>UV</sup><sub>h</sub>.

</AnnotPart>
<AnnotPart fig="mla-flow/01-projections" panels="3">

**Shared rotary key.** One 64-dimensional K<sup>R</sup> with RoPE applied is **shared by all heads** and stored in the cache. Position information goes only into this K<sup>R</sup>; C<sup>KV</sup> gets no RoPE. Why the positional part is kept separate has to do with "absorption," so it is explained after absorption.

</AnnotPart>
</Annot>

What stays in the cache is **C<sup>KV</sup> (512 dimensions) and K<sup>R</sup> (64 dimensions)**.

<details>
<summary>More: RoPE's rotation and the position difference</summary>

RoPE pairs up a vector's dimensions and rotates each pair by an angle proportional to the position. When a Query at position t and a Key at position s are each rotated and then dotted, the two rotations combine into a single rotation by the difference in position. That is why the score depends on relative distance rather than absolute position. Position information thus enters the score, where Query and Key meet, as a rotation R(t − s) that differs with the position difference. V4's inverse rotation, seen later, uses the same property.

</details>

### Content score and positional score

Figure 4 splits the attention computation of one head into two lines. The top line goes from scores to probabilities; the bottom line uses the probabilities to weight the Values and produce the output.

<Annot fig="mla-flow/02-attention" n={4} layout="stack" textHead>
<AnnotPart fig="mla-flow/02-attention" panels="1">

**① From scores to probabilities.** The score is the sum of two parts: the content score Q<sup>C</sup><sub>h</sub> (K<sup>C</sup><sub>h</sub>)<sup>T</sup>, from multiplying content components, and the positional score Q<sup>R</sup><sub>h</sub> (K<sup>R</sup>)<sup>T</sup>, from multiplying positional components. This equals the dot product of a Query and Key formed by concatenating the two components. Dividing the summed score S<sub>h</sub> by √(d<sub>k</sub> + d<sub>r</sub>) and applying the causal mask and softmax gives the probabilities P<sub>h</sub>.

</AnnotPart>
<AnnotPart fig="mla-flow/02-attention" panels="2">

**② On to the output.** The probabilities P<sub>h</sub> weight V<sub>h</sub> to give Z<sub>h</sub>; the results of all heads are concatenated and projected by W<sup>O</sup>.

</AnnotPart>
</Annot>

From this figure alone, MLA looks as if it still expands every head's Key and Value for the computation. Then storage would be small, but each step would need computation to rebuild Key and Value. Decode avoids this rebuilding with **absorption**, which changes the order of the multiplications.

### Computing without expanding Key and Value

Figure 5 computes the same content score in three ways. The three lines are not steps run one after another; they are three orders of computation that give the same result from the same C<sup>Q</sup> and C<sup>KV</sup>.

<Annot fig="mla-flow/03-key-absorption" n={5} layout="stack" textHead>
<AnnotPart fig="mla-flow/03-key-absorption" panels="1">

**① Expand.** As in Figure 4, build the per-head K<sup>C</sup><sub>h</sub>, then multiply by the Query. The dot product runs over d<sub>k</sub> dimensions.

</AnnotPart>
<AnnotPart fig="mla-flow/03-key-absorption" panels="2">

**② Absorb.** Only the parentheses move. By associativity of matrix multiplication, Q<sup>C</sup><sub>h</sub> (C<sup>KV</sup> W<sup>UK</sup><sub>h</sub>)<sup>T</sup> = (Q<sup>C</sup><sub>h</sub> (W<sup>UK</sup><sub>h</sub>)<sup>T</sup>) (C<sup>KV</sup>)<sup>T</sup>. Multiplying W<sup>UK</sup><sub>h</sub> on the Query side first gives a 512-dimensional Q̂<sub>h</sub>, which is multiplied directly with C<sup>KV</sup> from the cache. K is never expanded.

</AnnotPart>
<AnnotPart fig="mla-flow/03-key-absorption" panels="3">

**③ Pre-merge the weights.** The two Query-side weights are merged into one in advance: Ŵ<sup>Q</sup><sub>h</sub> = W<sup>UQ</sup><sub>h</sub> (W<sup>UK</sup><sub>h</sub>)<sup>T</sup>. This is mathematically the same, but the merged weight can be larger, so real implementations do not necessarily use it.

</AnnotPart>
</Annot>

The three forms produce algebraically the same content score. With finite precision and quantization, rounding error can differ slightly. All three only change the order in which the content score is computed; the positional score Q<sup>R</sup><sub>h</sub> (K<sup>R</sup>)<sup>T</sup> and the scaling by √(d<sub>k</sub> + d<sub>r</sub>) (a divisor of the score, unlike the scales stored with quantized values) stay as they are.

With absorption, the dot product at each position runs over r<sub>kv</sub> (512) instead of d<sub>k</sub> (128), four times longer. In exchange, multiplying every cached position by W<sup>UK</sup><sub>h</sub> to expand the Key (a 512×128 product per position) and reading that expanded Key both disappear; the Query side multiplies by W<sup>UK</sup><sub>h</sub> just once. In decode, with a single Query, this difference is large and absorption wins. In prefill, with many Queries, a Key expanded once is shared by all of them, so computing with the expanded Key can be better.

**Why the positional part is kept separate.** Absorption builds one Q̂<sub>h</sub> and multiplies it with C<sup>KV</sup> at every position, so nothing between the Query and C<sup>KV</sup> may change from position to position. If RoPE were applied to the content Key built from C<sup>KV</sup>, then in the figures' row-vector notation the score at position s would take the form q R(t − s) (W<sup>UK</sup><sub>h</sub>)<sup>T</sup> c<sub>s</sub><sup>T</sup> (c<sub>s</sub> is C<sup>KV</sup> at position s). An R(t − s) that differs by position sits in between, so no single Q̂<sub>h</sub> exists. That is why MLA puts position information only into the small K<sup>R</sup> with RoPE, and uses absorption only on the content part, which has no RoPE ([MLA storage article](/en/posts/model-advanced-mla-storage/)).

With the score in hand, the same can be done for how the probabilities combine the Values. The three lines of Figure 6 are again three orders of computation with the same result. In Figure 6, W<sup>O</sup><sub>h</sub> is the block of rows of Figure 4's output weight W<sup>O</sup> that belongs to head h, and Y<sub>h</sub> is head h's contribution to the final output. Adding Y<sub>h</sub> over all heads gives Figure 4's Y.

<Annot fig="mla-flow/04-value-absorption" n={6} layout="stack" textHead>
<AnnotPart fig="mla-flow/04-value-absorption" panels="1">

**① Expand.** Expand V<sub>h</sub> to [T, d<sub>v</sub>], then take its weighted sum with the probabilities P<sub>h</sub>.

</AnnotPart>
<AnnotPart fig="mla-flow/04-value-absorption" panels="2">

**② Absorb.** First, use the probabilities to take a weighted sum of the rows of C<sup>KV</sup>, giving U<sub>h</sub>. Then multiply U<sub>h</sub> by W<sup>UV</sup><sub>h</sub> and the output weight. the Value is never expanded: expanding means building the Value for all T positions, while ② multiplies W<sup>UV</sup><sub>h</sub> only into the result after weighting (one row in decode).

</AnnotPart>
<AnnotPart fig="mla-flow/04-value-absorption" panels="3">

**③ Pre-merge the weights.** W<sup>UV</sup><sub>h</sub> and W<sup>O</sup><sub>h</sub> are merged into one in advance: Ŵ<sup>O</sup><sub>h</sub> = W<sup>UV</sup><sub>h</sub> W<sup>O</sup><sub>h</sub>.

</AnnotPart>
</Annot>

Swapping the order of the weighted sum and the matrix multiplication gives the same result. This way, a decode step completes its computation while **reading only C<sup>KV</sup> and K<sup>R</sup> from the cache**. The derivation of absorption is traced with a small example in the [MLA computation article](/en/posts/model-advanced-mla-computation/).

### Working out V2's number

Now V2's number follows. Each layer stores 512 dimensions of C<sup>KV</sup> and 64 of K<sup>R</sup>.

```text
V2: 60 layers × (C^KV 512 + K^R 64) × 2 B = 69,120 B  (about 1/57 of MHA)
```

V3 has the same MLA structure with 61 layers, so 61 × 576 × 2 = 70,272 B. That is why this article does not treat V3 separately.

MLA cut storage sharply, but the **range that is read** is unchanged. Each decode step still reads C<sup>KV</sup> at every earlier position. In a 128K context, V2 reads 60 layers × 131,072 × 1,152 B ≈ 9.06 GB (1,152 B = (C<sup>KV</sup> 512 + K<sup>R</sup> 64) × 2 B) per step. That is far less than MHA's 515 GB, but it keeps growing as the context gets longer.

## DeepSeek-V3.2

V3.2 keeps MLA and adds **DSA** (DeepSeek Sparse Attention) to choose **which positions to read**. A small lightning indexer scores positions and picks up to 2,048 of them, and the main attention uses only the picked positions. According to the report, the indexer is trained to follow the probability distribution the main attention actually produces. Below we look at how the search key is built, the score that picks positions, and the main attention over the picked positions, and then work out storage and reads. Figure 7 shows the effect.

### DSA: three things the indexer builds

The indexer is a small module that picks the positions to read in a way similar to the scoring part of attention. It does not weight Values into an output. Values on the indexer side carry the superscript I (indexer): q<sup>I</sup><sub>j</sub> is the query of indexer head j, k<sup>I</sup> is the search key, w<sup>I</sup> is the head weight, and the weights that produce them are W<sup>IQ</sup>, W<sup>IK</sup>, and W<sup>Iw</sup>. The subscript j numbers indexer heads, which are separate from the main attention's heads h. As Figure 8 shows, the indexer builds three things.

<Annot fig="dsa-flow/01-indexer-projections" n={8} layout="stack" textHead>
<AnnotPart fig="dsa-flow/01-indexer-projections" panels="1">

**Indexer query.** q<sup>I</sup><sub>j</sub> is built for each head j from MLA's Query latent C<sup>Q</sup> (number of indexer heads H<sup>I</sup> = 64, width per head d<sup>I</sup> = 128). It reuses the same latent as the main attention.

</AnnotPart>
<AnnotPart fig="dsa-flow/01-indexer-projections" panels="2">

**Search key** (labeled indexer key). **Only one** k<sup>I</sup> is built from the input X and shared by all indexer heads. This value **builds up in the cache**, because later tokens need k<sup>I</sup> at each earlier position to evaluate it. The RoPE in the figure applies to 64 of the 128 dimensions, and LayerNorm is a normalization that sets a vector's mean and variance. Compared at the same precision, this extra key increases storage.

</AnnotPart>
<AnnotPart fig="dsa-flow/01-indexer-projections" panels="3">

**Head weights.** w<sup>I</sup> is built from X and sets, for each token, how much each of the 64 heads' judgments counts.

</AnnotPart>
</Annot>

### The score that picks positions

The indexer combines its query, key, and head weights to rank the positions each query may read. Figure 9 draws the scores of all queries as one [T, T] matrix: rows are queries and columns are candidate positions. ⊙ is an element-wise product; the head weight w<sup>I</sup><sub>j</sub> has one value per query row, so that value multiplies every candidate score in the row.

<Annot fig="dsa-flow/02-index-score" n={9} layout="stack" whole textHead>
<AnnotPart fig="dsa-flow/02-index-score" panels="1" xr="0.03-0.887">

For each head, take the dot product of the query and the shared key, apply ReLU (which turns negatives into 0), and multiply the result by the head weight. Then sum over all heads.

From the score I, each row picks up to 2,048 highest-scoring positions among the positions that query can see (itself included), giving a selection mask M: 0 for picked positions and −∞ for the rest.

</AnnotPart>
</Annot>

In the report's notation:

```text
I(t, s) = Σⱼ w^I(t, j) × ReLU( q^I(t, j) · k^I(s) )
```

The indexer has no softmax, and w<sup>I</sup> is not a probability. The score is used only for ranking.

### MLA that reads only the picked positions

Once the selection is set, the main attention keeps probability only at those positions. Figure 10 is ② of Figure 5, absorbed MLA, with the selection mask M added.

<Annot fig="dsa-flow/03-sparse-attention" n={10} layout="stack" whole textHead>
<AnnotPart fig="dsa-flow/03-sparse-attention" panels="1" xr="0.018-0.941">

The score is computed exactly as in absorbed MLA. The figure leaves out scaling. M is 0 only at picked positions among those the query can see, so it also does the job of the causal mask.

### Working out V3.2's number

Start with the structure alone. What is stored is MLA's 576 dimensions plus a 128-dimensional search key, 704 dimensions in all. If everything were stored in BF16, that would be 61 layers × 704 × 2 B = 85,888 B, 22% more than V3 (70,272 B). **DSA is not a technique for reducing storage.** Unpicked positions are not removed from the cache either, because the next token may pick different positions.

Real deployments store at lower precision. For one token in one layer, two groups of values are stored.

**Main KV, 656 B.** The 512 dimensions of C<sup>KV</sup> are stored in FP8 at 1 B per element, 512 B. FP8 has a narrow representable range, so a **scale** factor for each group of values is stored with it. There is one FP32 scale per 128 dimensions, so 4 × 4 B = 16 B. The 64 dimensions of the positional Key K<sup>R</sup> are not quantized and stay in BF16, 64 × 2 B = 128 B. Together, 512 + 16 + 128 = 656 B.

**Search key, 132 B.** The 128 dimensions of the search key k<sup>I</sup> are stored in FP8 for 128 B, with one FP32 scale for all 128 dimensions, 4 B. 128 + 4 = 132 B. The search key is quantized to FP8 entirely, including the dimensions RoPE is applied to; unlike the main KV, no part of it is left in BF16.

```text
Main KV:     C^KV 512 × 1 B + scale 4 × 4 B + K^R 64 × 2 B = 512 + 16 + 128 = 656 B
Search key:  k^I 128 × 1 B + scale 1 × 4 B               = 128 + 4        = 132 B
V3.2: 61 layers × (656 + 132) B = 48,068 B  (about 1/82 of MHA)
```


### Looking at reads

What DSA cuts is what one decode step **reads**. The right chart of Figure 7 shows what all layers read to generate one token (one decode step) in a 128K context. Each bar is colored in proportion to the KV read by attention (blue) and the search keys read to pick positions (red). Each cache item a layer references is counted once. A cache shared by several layers is counted again for each layer that reads it, but it is not counted twice because of multiple heads in the same layer or the two roles of Key and Value. SWA, scales and padding inside a cache item are included; reading the same values more than once and writes of the new cache are excluded.

This value assumes that only the selected KV and the candidate search keys are read, and computes each cache item's size in the same deployed cache format as storage. It is a computed amount, not actual memory traffic. The reads if everything were stored in BF16 are collected in the box at the end of this section.

In V3.2, the KV read by attention is 61 layers × 2,048 positions × 656 B ≈ 82 MB. Position selection cuts the positions each layer reads from 131,072 to 2,048, to 1/64, and storing the main KV at lower precision adds to that. In exchange, the indexer scans the keys of every position: 61 layers × 131,072 × 132 B ≈ 1.06 GB. The total is about 1.14 GB, and search keys make up about 93% of it. That alone does not mean picking positions takes most of the execution time, because computation and actual memory access patterns differ.

The indexer is still cheaper than reading every position with the main attention because each key is small (128 dimensions, FP8), every head reads the same key, and there is no softmax, only ReLU and a weighted sum. But it still scans the whole context. Cutting this cost together with storage is the task V4 takes on. How the indexer works is covered in the [sparse indexer article](/en/posts/model-advanced-sparse-indexer/).

## DeepSeek-V4-Flash

V4 uses **compression along tokens**: it merges the KV of several tokens and stores the result as one vector. This one compressed vector is called an **entry**. It mixes two schemes with different compression ratios across layers. **CSA** (Compressed Sparse Attention) compresses overlapping spans into one entry every 4 tokens and reads selectively with an indexer. **HCA** (Heavily Compressed Attention) compresses 128 non-overlapping tokens into one entry and reads every completed entry. Recent positions are kept separately without compression. Below we start with HCA, which is simpler, move on to CSA, and then work out the numbers. Figure 11 shows the effect.

<Annot fig="deepseek-kv-cache/03-guide-v4" n={11} layout="cols" textHead>
<AnnotPart fig="deepseek-kv-cache/03-guide-v4" panels="1">

V4-Flash uses about **3,514 B** per token. The local KV that keeps recent positions is listed separately in orange.

</AnnotPart>
<AnnotPart fig="deepseek-kv-cache/03-guide-v4" panels="2">

Reads under the same conditions are about **68 MB**.

</AnnotPart>
</Annot>

This article uses V4-Flash as its reference. Of its 43 layers, the first 2 are SWA layers that see only recent positions; 21 are CSA and 20 are HCA. It is also worth noting up front that V4 is not MLA with a compressor added. V4 does not expand per-head Key and Value from a latent the way MLA does. **A single 512-dimensional entry serves as both Key and Value for every head.** There are no weights like MLA's W<sup>UK</sup> and W<sup>UV</sup> that expand Key and Value; each head's Query is multiplied with the entry directly (Figure 15).

### HCA: 128 tokens into one

In this article, the uncompressed KV of the last 128 positions is called the **local KV (SWA)**. SWA (sliding window attention) is attention that reads only the recent positions. What is compressed and built up across a long context splits in two. The compressed KV that attention actually reads is the **main KV**, and CSA, shown later, adds search keys that pick positions to read. The main KV and search keys together are the **global KV**. Here "local" refers to the range of recent positions. The V4 report describes the branch that reads recent positions as sliding window attention; the names local KV, main KV, and global KV come from the V4.1 report.

From V4 on, the notation changes a little. c<sup>Q</sup> is a small Query latent, like MLA's C<sup>Q</sup>. W<sup>KV</sup><sub>win</sub> builds the local KV of the recent window (win), and W<sup>KV</sup><sub>comp</sub> builds the candidates to compress (compression). Here **C is not MLA's content part but the candidate values to compress**, and **Z is not MLA's head output but the pre-softmax score of each candidate**. A finished compressed entry is written C<sup>Comp</sup> (compressed).

RMSNorm is a normalization that keeps a vector's size constant. In Figure 12, c is the width of one entry (512), and an entry of this width serves as both Key and Value. n<sub>h</sub> is the number of heads. E<sup>win</sup> is a local KV entry of the recent window. Figure 12 leaves out the RoPE step; its form after RoPE is in the comparison part of Figure 13.

An HCA layer builds three branches from the input X.

<Annot fig="hca-flow/01-weight-map" n={12} layout="stack" textHead>
<AnnotPart fig="hca-flow/01-weight-map" panels="1">

**Query.** Built through a latent c<sup>Q</sup>, as in MLA.

</AnnotPart>
<AnnotPart fig="hca-flow/01-weight-map" panels="2">

**Local KV.** Built one per token without compression, keeping only the last 128.

</AnnotPart>
<AnnotPart fig="hca-flow/01-weight-map" panels="3">

**Compressed KV.** Builds candidates C and scores Z, then merges m′ tokens into one entry.

</AnnotPart>
</Annot>

Compression is a weighted average computed separately for each channel (one feature column). In the figure, the subscript b is the block number (a block is the m′ tokens compressed together), S<sub>b</sub> the weights set by softmax, and u<sub>b</sub> the merged row. For teaching, m′ is reduced to 4; a real HCA layer uses m′ = 128.

<Annot fig="hca-flow/02-compression" n={13} layout="stack" textHead>
<AnnotPart fig="hca-flow/02-compression" panels="1" yr="0.009-0.759">

**①② Set the weights and merge.** The position bias B is added to the scores Z of the tokens in the block, and a softmax along the token direction sets the weights. B is a value learned for each position (offset) within a block, and every block uses the same B. Merging the candidates C channel by channel with those weights leaves one row.

**③ Finish the entry.** The merged row goes through RMSNorm and RoPE to become an entry. An entry is complete only once its block is full. The 'learned scale' in the figure is a learned weight multiplied after RMSNorm, not the scale used for FP8 storage. RoPE is applied only to the last 64 dimensions of an entry.

</AnnotPart>
<AnnotPart fig="hca-flow/02-compression" panels="1" yr="0.759-0.987">

**Compare.** The local KV is built separately for each token, without compression.

</AnnotPart>
</Annot>

A compressed entry can be read only once its block is full. Figure 14 shows how the entries a token can read change as one more token arrives.

<Annot fig="hca-flow/03-visible-entries" n={14} layout="stack" textHead>
<AnnotPart fig="hca-flow/03-visible-entries" panels="1" yr="0.014-0.515">

**t = 6.** Token t reads all completed compressed entries concatenated with the recent window, which includes the current token. Here only block 0 is complete, and the recent tokens of the still incomplete block 1 are read through the window.

</AnnotPart>
<AnnotPart fig="hca-flow/03-visible-entries" panels="1" yr="0.515-0.92">

**t = 7.** Block 1 is now complete too, adding one compressed entry. The window is read as well, so the same original token can appear in both a compressed entry and a window entry.

</AnnotPart>
</Annot>

Attention then uses the entries gathered this way as both Keys and Values.

<Annot fig="hca-flow/04-attention" n={15} layout="stack" textHead>
<AnnotPart fig="hca-flow/04-attention" panels="1">

**① Prepare the query, score.** The query is normalized per head with RMSNorm (head RMS) and rotated with RoPE for position t, then multiplied with the N<sub>t</sub> entries E gathered in Figure 14 to give the scores S. Here E plays the **Key** role. There are no weights that expand per-head Key and Value.

</AnnotPart>
<AnnotPart fig="hca-flow/04-attention" panels="2">

**② Softmax with a sink.** Each head adds exp(z′ₕ), from a learned value z′ₕ, to the softmax denominator, so the weights on the real entries can sum to less than 1. This value, the **sink**, leaves room to pay less attention to every entry.

</AnnotPart>
<AnnotPart fig="hca-flow/04-attention" panels="3">

**③ Weighted sum, inverse rotation.** The probabilities P weight **the same E, now as the Value**, giving the head outputs O. E serves as the Value with RoPE still applied, so the last 64 dimensions of the output are rotated back by the current query position t (**inverse rotation**). The entry at position s had been rotated by s, so after the inverse rotation each entry's contribution is rotated by s − t: by relative distance rather than absolute position. The reasoning is in the 'RoPE's rotation' box in the V2 section.

</AnnotPart>
<AnnotPart fig="hca-flow/04-attention" panels="4">

**④ Grouped output projection.** The heads of O, rotated back in ③, are put into g groups. The width of one group, c<sub>g</sub>, is the outputs of its heads concatenated. Each group is reduced to width r<sub>o</sub> with its own W<sup>O,a</sup><sub>g</sub>, the results are concatenated, and a shared W<sup>O,b</sup> maps them back to the hidden size D.

</AnnotPart>
</Annot>

Since Key and Value are the same entry, it only needs to be stored once.

### CSA: compress with overlap and read selectively

CSA adds two things to the same frame as HCA. Compression spans overlap, and an indexer picks which entries to read.

<Annot fig="csa-flow/01-weight-map" n={16} layout="stack" textHead>
<AnnotPart fig="csa-flow/01-weight-map" panels="1">

**Query and indexer.** The Query path is the same as in HCA. The new indexer projects the Query latent it shares with the main attention to build the indexer query.

</AnnotPart>
<AnnotPart fig="csa-flow/01-weight-map" panels="2">

**Compressed KV.** The weights for candidates C and scores Z are twice as wide as in HCA, because each span is compressed with an overlap into its neighbor.

</AnnotPart>
</Annot>

Why the candidate weights are twice as wide shows up in how one entry is built. W<sup>KV</sup><sub>comp</sub> and W<sup>Z</sup> give each token candidates and scores 2c wide, used as a first half a and a second half b. The second half b goes into the entry of the token's own span, and the first half a goes into the entry of the next span as its 'previous span'. So one entry gathers 8 rows, a from the 4 tokens of the previous span and b from the 4 tokens of its own span, and merges them the same way as HCA. The softmax over these 8 rows' scores, with the position bias added, gives the weights used for compression.

<Annot fig="csa-flow/02-overlap-compression" n={17} layout="stack" textHead>
<AnnotPart fig="csa-flow/02-overlap-compression" panels="1" yr="0.008-0.796">

**①② One entry from 8 tokens.** One CSA entry reads 8 tokens: the 4 tokens of its own span (b) and the 4 of the previous span (a). m = 4 is CSA's real value.

**③ Finish the entry.** Even so, one entry is produced every 4 tokens. The compression ratio is 4, so the number of stored entries is 1/4 of the number of tokens. As in HCA, an entry's RoPE position is the first token of its own span (p = 4 in the figure); reading the previous span as well does not change that.

</AnnotPart>
<AnnotPart fig="csa-flow/02-overlap-compression" panels="1" yr="0.796-0.948">

**Neighboring entries.** Neighboring entries share half of their source tokens, so information from both sides of a block boundary can be reflected. This is weighted compression, so it does not mean the information is preserved as is, and the first entry has no previous span.

</AnnotPart>
</Annot>

CSA reads only some of the compressed entries, so it needs an indexer to decide which ones.

<Annot fig="csa-flow/03-indexer" n={18} layout="stack" textHead>
<AnnotPart fig="csa-flow/03-indexer" panels="1" yr="0.025-0.677">

**①②③ Key, query, head weights.** In the figure, n<sub>I</sub> is the number of indexer heads, d<sub>I</sub> the width per head (the same as V3.2's H<sup>I</sup> and d<sup>I</sup>), and N<sub>s</sub> the number of compressed entries completed so far. CSA's indexer uses the same score formula as V3.2's, but builds its keys with a **separate compressor**. So search keys are also stored one per 4 tokens, with 128 dimensions. This compressor builds its own candidates and scores Z<sup>I</sup> from X the same way as the main compressor and builds one entry per 4 tokens with the same overlap, so search key s and main entry s stand for the same span of original tokens.

</AnnotPart>
<AnnotPart fig="csa-flow/03-indexer" panels="1" yr="0.677-0.947">

**④ Score and select.** Scores are combined with the head weights, and the highest-scoring blocks are picked for each token. Blocks not yet complete at that query position are not candidates.

</AnnotPart>
</Annot>

Adding the recent window to the picked compressed entries settles what this token reads.

<Annot fig="csa-flow/04-visible-entries" n={19} layout="stack" textHead>
<AnnotPart fig="csa-flow/04-visible-entries" panels="1" xr="0-0.931">

Token t reads the k compressed entries picked by the indexer plus the recent window. This differs from HCA, which reads **all** compressed entries.

HCA compresses 128×, so there are few entries and reading them all is fine. CSA compresses 4×, so there are many entries, and it reads selectively.

</AnnotPart>
</Annot>

### Working out V4-Flash's number

CSA layers store a 512-dimensional main KV entry and a 128-dimensional search key every 4 tokens, and HCA layers store a 512-dimensional main KV entry every 128 tokens.

On structure alone, even if everything were stored in BF16, that is 21 × 640 × 2 B ÷ 4 + 20 × 512 × 2 B ÷ 128 = 6,880 B, about one-tenth of V2. The width of the stored vector (512) is close to MLA's 576, but 4 and 128 tokens are compressed into one entry.

The deployed format stores main KV entries mostly in FP8 and search keys in FP4. The format used in this article is 584 B per main KV entry and 68 B per search key.

```text
V4-Flash: 21 layers × (584 + 68) B ÷ 4 + 20 layers × 584 B ÷ 128 ≈ 3,514 B  (about 1/1,119 of MHA)
```

<details>
<summary>More detail: the V4-Flash cache format</summary>

```text
Main KV entry: 448 non-RoPE dims × 1 B (FP8 E4M3) + 64 RoPE dims × 2 B (BF16)
               + one UE8M0 scale per 64 channels, 1 B × 7 + padding 1 B = 584 B
Search key:    128 dims × 0.5 B (FP4 E2M1)
               + one UE8M0 scale per 32 channels, 1 B × 4 = 68 B
```

In the format names, the numbers after E and M are the exponent and mantissa bits, and UE8M0 is an 8-bit scale that only represents powers of two.

</details>

On top of this there is a separate **local KV cache**. All 43 layers keep the KV of the last 128 positions without compression. In the deployed format that is 43 × 128 × 584 B ≈ 3.2 MB. This value stops growing once the last 128 positions are filled. But as the per-token growth shrank, local KV became a larger share of storage. Approximating global KV as per-token growth × context length, the two are about equal at roughly 900 tokens. For shorter contexts, the local KV cache is larger. The approximation ignores rounding of compressed blocks and intermediate compression state.

Reads (the right chart of Figure 11) also dropped. The KV read by attention is about 21.5 MB, and the keys read by the indexer about 46.8 MB. The KV is (21 CSA layers × (512 picked + 128 window) + 20 HCA layers × (N/128 + 128) + 2 SWA layers × 128) cache items at 584 B each, since compressed entries and uncompressed window positions are stored in the same format. That is far less than V3.2's 1.06 GB because search keys are compressed 4×, only 21 layers use the indexer, and each key shrinks from 132 B to 68 B. HCA layers read every compressed entry, so that part keeps growing in proportion to context.

The 40 layers of V4.1-Flash split into the first 20 (encoder) and the last 20 (decoder). ### CSA2: compression without overlap, and the search key

CSA2 changes two things within a layer. Compression spans no longer overlap, and the search key is built from the main KV instead of by a separate compressor.

<AnnotPart fig="csa2-flow/07-compression-span" panels="1">

**CSA.** One entry reads its own span together with the previous span, sharing half of its tokens with the neighboring entry.

</AnnotPart>
<AnnotPart fig="csa2-flow/07-compression-span" panels="2">

**CSA2.** Spans do not overlap, so each token goes into exactly one entry. The position bias B inside the compressor is gone as well.

The compression ratio also dropped. In real CSA2, encoder layers pack 2 tokens into one entry (m = 2), and decoder layers build one entry per token without compression (m = 1). ### Sharing KV across layers: Full, Reindex, Reuse

Until now, every layer stored its own KV. In V4.1-Flash, **four Full layers build and store global KV**, and the remaining CSA2 layers share it. The first two layers use SWA only, and all 40 layers build their own local KV.

Each CSA2 layer is fixed to one of three modes.

<Annot fig="csa2-flow/01-three-modes" n={23} layout="stack" textHead>
<AnnotPart fig="csa2-flow/01-three-modes" panels="1">

A **Full** layer builds new main KV and search keys and picks its top-k with its own indexer. **Only Full layers store global KV.** Full is not dense attention over every position either; it reads only the top-k.

A **Reindex** layer borrows the main KV and search keys of the most recent preceding Full layer and picks positions again with its own indexer query.

A **Reuse** layer has no indexer. It borrows both the main KV and the selection list from earlier layers.

</AnnotPart>
<AnnotPart fig="csa2-flow/01-three-modes" panels="2">

**Common to all three modes.** The picked main KV rows are joined with this layer's local KV, and attention is computed with this layer's Query. The figure draws it once, but every layer computes it on its own.

</AnnotPart>
</Annot>

What is shared is the global KV and the selection list, not the result of attention. Sharing works even though each layer's representation differs because the model is trained from the start with this sharing. The principle of cross-layer sharing is covered in the [cross-layer KV sharing article](/en/posts/model-advanced-cross-layer-kv/).

### CED: the decoder's global KV comes from the encoder

V4.1's encoder and decoder both process the same token sequence causally. In decode, the current token passes through the 20 encoder layers and then the 20 decoder layers in turn. This structure is called **CED** (Causal Encoder-Decoder). The difference lies in where the KV that decoder layers read is built.

<Annot fig="deepseek-kv-cache/06-ced-sources" n={26} layout="stack" textHead>
<AnnotPart fig="deepseek-kv-cache/06-ced-sources" panels="1" xr="0-0.988">

**Left: the layer stack.** Token t passes through the layers from bottom to top. The decoder's global KV (main KV and search keys) is built not from the decoder's own hidden states but from the **encoder's final output**. The first decoder Full layer projects this output to build it, and the other decoder layers share it.

**Right: inside one decoder layer.** This layer builds the **main Query and local KV** from its own input. It then concatenates the main KV at positions picked with the search keys and its own local KV, scores them **with its own main Query**, and takes the weighted sum. Separately, the Full and Reindex layers score positions for selection with their own indexer query.

</AnnotPart>
</Annot>

Even when several layers share the global KV, the Query that reads it differs from layer to layer.

This split makes it possible to cut compute in prefill, where the prompt is processed.

<Annot fig="deepseek-kv-cache/07-ced-prefill" n={27} layout="stack" textHead>
<AnnotPart fig="deepseek-kv-cache/07-ced-prefill" panels="1" xr="0-0.993">

**Encoder layers** run over every position of the prompt. Their output builds the global KV that the decoder reads, for every position.

The only cache left to prepare by running the decoder is each decoder layer's **local KV**, and local KV needs only the last 128 positions. So **decoder layers run only over the positions in the recent window.** The report calls this run **replay**. The decoder has not passed over those positions before; the name means only the recent span is sent through the decoder. The decoder output at the last prompt position gives the first token, and after that decode runs all 40 layers.

</AnnotPart>
</Annot>

Replay does more than project KV. It passes the recent positions through the decoder layers in order, running attention and the FFN as well. The first decoder layer takes the encoder output at those positions, each later layer takes the output of the decoder layer just below it, and during the run each layer also reads its selected entries from the global KV.

For long prompts, the number of (position, layer) evaluations in prefill is roughly halved, since the 20 decoder layers run only over the recent span rather than the whole prompt. This cuts **prefill compute**, not the KV cache, and it is a ratio of evaluations, not of time.

Replay is also an approximation. Computing the hidden state at the first position of the recent span exactly would need local KV from positions before it, and replay cuts off that reference. The savings apply only to prefill. In decode, which generates new tokens, all 40 encoder and decoder layers run.

This way of running is described in the report; the public reference code reviewed here does not implement it separately. CED is covered in more detail in the [CED article](/en/posts/model-advanced-ced/).

### Working out V4.1-Flash's number

Four layers store global KV. The 3 encoder Full layers store one entry every 2 tokens, and the 1 decoder Full layer stores one entry per token. One entry is 512 dimensions of main KV plus 128 of search key.

On structure alone, if everything were stored in BF16, that is (3 ÷ 2 + 1) × (512 + 128) × 2 B = 3,200 B, about half of V4-Flash. The compression ratio actually went down (4 → 2 and 1), but the number of layers storing global KV fell from 41 (21 CSA + 20 HCA) to 4.

The deployed format stores main KV entries in FP4: 512 dimensions × 0.5 B = 256 B, plus one FP8 (E4M3) scale of 1 B per 16 channels, 32 B, for 288 B. The RoPE part is quantized as well. Search keys are 68 B, the same as V4.

```text
V4.1-Flash: (3 ÷ 2 + 1) × (288 + 68) B = 2.5 × 356 = 890 B  (about 1/4,418 of MHA)
```

All 40 layers keep local KV for the last 128 positions. In the deployed format (all 512 dimensions in FP8, RoPE part included, with one UE8M0 scale per 32 channels, 528 B per token), that is 40 × 128 × 528 B ≈ 2.7 MB. Using the same approximation against 890 B per token, the two are about equal at roughly 3,038 tokens. For shorter contexts, keeping recent positions is actually the main storage cost.

For reads (the right chart of Figure 20), the KV read by attention is about 8.3 MB and the keys read by the indexer about 26.7 MB. The KV reads are main KV, 5.6 MB at 288 B per entry, plus local KV, 2.7 MB at 528 B. For search keys, the 3 encoder Full layers read N/2 each, the decoder Full layer reads N, and the 4 Reindex layers read 16,384 candidates each: (3 × N/2 + N + 4 × 16,384) × 68 B. Sharing KV does not stop each layer from computing attention, so each of the 38 CSA2 layers reads 512 main entries. Storage is one copy, but reads happen in every layer.

## What was cut and what remains

Putting the five models together again, each generation cut a different factor.

| Model | What changed | Factor reduced | KV per token (deployed format, local KV separate) |
| --- | --- | --- | --- |
| Hypothetical MHA | baseline | N/A (baseline) | 3,932,160 B (BF16 assumed) |
| V2 | MLA | width of the stored vector | 69,120 B (BF16) |
| V3.2 | DSA, FP8 KV | positions read (storage grows structurally) | 48,068 B |
| V4-Flash | CSA and HCA, shared K = V | compression along tokens (4 or 128 into one) | 3,514 B |
| V4.1-Flash | CSA2, FP4 KV (CED cuts prefill compute) | layers that store global KV | 890 B |

Precision also went down from generation to generation. Going from BF16 to FP8 and then FP4 roughly halved storage, and then halved it again, even for the same structure.

The costs that remain are also clear. First, the **local KV cache** stays at a fixed size once the last 128 positions are filled, and its share grows as the per-token growth shrinks. Second, there is the **cost of picking positions**. In the right chart of Figure 1, most of what the sparse models read is search keys. Third, compression, selection, and CED's replay involve **approximation**. Compression and selection are part of the structure the models are trained with, while replay is an approximation in how prefill is run. Either way, MHA-level quality cannot be assumed; quality has to be judged from the evaluations in the reports.

Finally, storage falling to 1/4,400 does not make decode 4,400 times faster. Real speed depends on compute, kernel implementation, memory layout, and batch size.
