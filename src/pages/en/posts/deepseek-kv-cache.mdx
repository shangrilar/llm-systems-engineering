One of the main costs of long-context inference is the **KV cache**: the Keys and Values of earlier positions, stored so they do not have to be recomputed every time a new token is generated. As the [KV cache article](/en/posts/inference-kv-cache/) showed, this storage grows in proportion to context length and is multiplied by the number of requests served at once. So how much the cache grows when the context gains one token goes a long way toward setting the cost of long-context inference.

DeepSeek changed its attention design several times between V2 and V4.1. This article follows those changes through one number, the **KV cache per token**. A hypothetical MHA model with V2's dimensions, storing every head's K and V, would use about 3.9 MB per token. V4.1-Flash uses 890 B per token, about 1/4,400 of that.

This reduction did not happen in a single step. The cache per token can be seen roughly as a product of four factors.

```text
KV cache per token ≈ width of the stored vector (dimensions)
                     × stored rows per token
                     × number of layers storing KV
                     × bytes per element
```

V2's MLA narrowed the **width of the stored vector**. V3.2's DSA reduced **the number of positions read**, rather than the amount stored. V4's CSA and HCA compress several tokens into one to reduce the **stored rows per token**, and V4.1's CSA2 lets layers share KV to reduce the **number of layers that store global KV**. Along the way, bytes per element also dropped from BF16 to FP8 and then FP4. Below, we look at what changed in each generation through figures and then work out the numbers ourselves.

<details>
<summary>More detail: how this article counts "KV cache per token"</summary>

- **Average growth in a long context.** Compressed models need 4 or 128 tokens to build one entry, so the same amount is not added at every token. We take the total cache divided by the number of tokens once the context is long enough.
- **One copy of the model body, one request.** B requests of the same length that do not share cache need B times the storage. Storage per GPU has to be worked out separately, depending on whether tensor parallelism splits or replicates the cache. The MTP module is excluded.
- **Search keys are included.** A search key is the small key an indexer scores to rank candidate positions; the flow diagrams label it "indexer key." From V3.2 on, models store these keys separately to pick positions to read. They also build up in proportion to context, so they are counted.
- **Storage uses the deployed cache formats chosen for this article, page padding included.** It can vary by engine and options.
- **The local KV cache that keeps only recent positions is listed separately.** Once the last 128 positions are filled it stops growing, so it is not part of the per-token growth. The local KV values in the figure are the data size of the last 128 positions, excluding spare page space and intermediate compression state.
- **These values are computed from model configs and cache formats, not measured on GPUs.**
- **The hypothetical MHA** is a reference that assumes V2's dimensions (60 layers, 128 heads, 128 dimensions per head) with every head's K and V stored. No such model exists, and it is not meant to be an MHA model of equal quality.

</details>

## The baseline: MHA that stores every head's K and V

The starting point is [core attention](/en/posts/core-attention/). In MHA, each layer builds a Key and a Value for every head and stores both in the cache. Plugging in V2's numbers, storing one token takes:

```text
Hypothetical MHA: 60 layers × 128 heads × (Key 128 + Value 128) × 2 B
                = 3,932,160 B ≈ 3.9 MB
```

At about 3.9 MB per token, a 128K-token context (131,072 positions) needs about 515 GB of cache for a single request. In decode, this whole cache is read for every new token. Storage and reads are both a problem. [MQA and GQA](/en/posts/model-advanced-mqa-gqa/) cut this value by letting several heads share K and V. DeepSeek took a different path.

### Content score and positional score

Figure 4 is the attention computation of one head.

<Annot fig="mla-flow/02-attention" n={4} layout="side" whole>
<AnnotPart fig="mla-flow/02-attention" panels="1" xr="0.173-0.849">

The score is the sum of two parts: the content score Q<sup>C</sup><sub>h</sub> (K<sup>C</sup><sub>h</sub>)<sup>T</sup>, from multiplying content components, and the positional score Q<sup>R</sup><sub>h</sub> (K<sup>R</sup>)<sup>T</sup>, from multiplying positional components. This equals the dot product of a Query and Key formed by concatenating the two components.

Then come scaling, the causal mask, and softmax, followed by a weighted sum of V. The results of all heads are concatenated and passed through the output projection.

From this figure alone, MLA looks as if it still expands every head's K and V for the computation. Then storage would be small, but each step would need computation to rebuild K and V. Decode with absorption avoids this rebuilding.

</AnnotPart>
<span slot="caption">Figure 4. Add two scores for attention.</span>
</Annot>

### Computing without expanding K and V

Figure 5 computes the same content score in three ways. All three start from the same C<sup>Q</sup> and C<sup>KV</sup>.

<Annot fig="mla-flow/03-key-absorption" n={5} layout="cols" whole>
<AnnotPart fig="mla-flow/03-key-absorption" panels="1" xr="0-0.329">

**① Expand.** As in Figure 4, build the per-head K<sup>C</sup><sub>h</sub>, then multiply by the Query. The dot product runs over d<sub>k</sub> dimensions.

</AnnotPart>
<AnnotPart fig="mla-flow/03-key-absorption" panels="1" xr="0.329-0.66">

**② Absorb.** Only the parentheses move. By associativity of matrix multiplication, Q<sup>C</sup><sub>h</sub> (C<sup>KV</sup> W<sup>UK</sup><sub>h</sub>)<sup>T</sup> = (Q<sup>C</sup><sub>h</sub> (W<sup>UK</sup><sub>h</sub>)<sup>T</sup>) (C<sup>KV</sup>)<sup>T</sup>. Multiplying W<sup>UK</sup><sub>h</sub> on the Query side first gives a 512-dimensional Q̂<sub>h</sub>, which is multiplied directly with C<sup>KV</sup> from the cache. K is never expanded.

</AnnotPart>
<AnnotPart fig="mla-flow/03-key-absorption" panels="1" xr="0.657-0.989">

**③ Pre-merge the weights.** The two Query-side weights are merged into one in advance. This is mathematically the same, but the merged weight can be larger, so real implementations do not necessarily use it.

</AnnotPart>
<span slot="caption">Figure 5. The same score without expanding K.</span>
</Annot>

The three forms produce algebraically the same content score. With finite precision and quantization, rounding error can differ slightly. All three only change the order in which the content score is computed; the positional score Q<sup>R</sup><sub>h</sub> (K<sup>R</sup>)<sup>T</sup> and the scaling stay as they are. The same can be done on the Value side.

<Annot fig="mla-flow/04-value-absorption" n={6} layout="cols" whole>
<AnnotPart fig="mla-flow/04-value-absorption" panels="1" xr="0-0.329">

**① Expand.** Expand V<sub>h</sub> to [T, d<sub>v</sub>], then take its weighted sum with the probabilities P<sub>h</sub>.

</AnnotPart>
<AnnotPart fig="mla-flow/04-value-absorption" panels="1" xr="0.329-0.66">

**② Absorb.** First, use the probabilities to take a weighted sum of the rows of C<sup>KV</sup>, giving U<sub>h</sub>. Then multiply U<sub>h</sub> by W<sup>UV</sup><sub>h</sub> and the output weight. V is never expanded.

</AnnotPart>
<AnnotPart fig="mla-flow/04-value-absorption" panels="1" xr="0.657-0.989">

**③ Pre-merge the weights.** W<sup>UV</sup><sub>h</sub> and W<sup>O</sup><sub>h</sub> are merged into one in advance.

</AnnotPart>
<span slot="caption">Figure 6. The same output without expanding V.</span>
</Annot>

Swapping the order of the weighted sum and the matrix multiplication gives the same result. This way, a decode step completes its computation while **reading only C<sup>KV</sup> and K<sup>R</sup> from the cache**. The derivation of absorption is traced with a small example in the [MLA computation article](/en/posts/model-advanced-mla-computation/).

### Working out V2's number

Now V2's number follows. Each layer stores 512 dimensions of C<sup>KV</sup> and 64 of K<sup>R</sup>.

```text
V2: 60 layers × (C^KV 512 + K^R 64) × 2 B = 69,120 B  (about 1/57 of MHA)
```

V3 has the same MLA structure with 61 layers, so 61 × 576 × 2 = 70,272 B. That is why this article does not treat V3 separately.

MLA cut storage sharply, but the **range that is read** is unchanged. Each decode step still reads C<sup>KV</sup> at every earlier position. In a 128K context, V2 reads 60 layers × 131,072 × 1,152 B ≈ 9.06 GB per step. That is far less than MHA's 515 GB, but it keeps growing as the context gets longer.

## DeepSeek-V3.2

V3.2 keeps MLA and adds **DSA** (DeepSeek Sparse Attention) to choose **which positions to read**. A small lightning indexer scores positions and picks up to 2,048 of them, and the main attention uses only the picked positions. ### The score that picks positions

<Annot fig="dsa-flow/02-index-score" n={9} layout="stack" whole>
<AnnotPart fig="dsa-flow/02-index-score" panels="1" xr="0.03-0.887">

For each head, take the dot product of the query and the shared key, apply ReLU, and multiply the result by the head weight. Then sum over all heads.

From the score I, up to 2,048 highest-scoring positions are picked per row, giving a selection mask M: 0 for picked positions and −∞ for the rest.

</AnnotPart>

In the report's notation:

```text
I(t, s) = Σⱼ w^I(t, j) × ReLU( q^I(t, j) · k^I(s) )
```

The indexer has no softmax, and w<sup>I</sup> is not a probability. The score is used only for ranking.

### Working out V3.2's number

Start with the structure alone. What is stored is MLA's 576 dimensions plus a 128-dimensional search key, 704 dimensions in all. Counted at the same BF16, that is 61 layers × 704 × 2 B = 85,888 B, 22% more than V3 (70,272 B). **DSA is not a technique for reducing storage.** Unpicked positions are not removed from the cache either, because the next token may pick different positions.

Real deployments store at lower precision. For one token in one layer, two groups of values are stored.

**Main KV, 656 B.** The 512 dimensions of C<sup>KV</sup> are stored in FP8 at 1 B per element, 512 B. FP8 has a narrow representable range, so a **scale** factor for each group of values is stored with it. There is one FP32 scale per 128 dimensions, so 4 × 4 B = 16 B. The 64 dimensions of the positional Key K<sup>R</sup> are not quantized and stay in BF16, 64 × 2 B = 128 B. Together, 512 + 16 + 128 = 656 B.

**Search key, 132 B.** The 128 dimensions of the search key k<sup>I</sup> are stored in FP8 for 128 B, with one FP32 scale for all 128 dimensions, 4 B. 128 + 4 = 132 B. The search key is quantized to FP8 including its RoPE part; unlike the main KV, no part of it is left in BF16.

```text
Main KV:     C^KV 512 × 1 B + scale 4 × 4 B + K^R 64 × 2 B = 512 + 16 + 128 = 656 B
Search key:  k^I 128 × 1 B + scale 1 × 4 B               = 128 + 4        = 132 B
V3.2: 61 layers × (656 + 132) B = 48,068 B  (about 1/82 of MHA)
```


### Looking at reads

What DSA cuts is what one decode step **reads**. The right chart of Figure 7 shows what all layers read to generate one token (one decode step) in a 128K context. Each bar is colored in proportion to the KV read by attention (blue) and the search keys read to pick positions (red). Each entry a layer references is counted once. A cache shared by several layers is counted again for each layer that reads it, but it is not counted twice because of multiple heads in the same layer or the two roles of K and V. SWA is included; repeated loads in practice and writes of the new cache are excluded.

This value is a BF16-equivalent logical amount that counts, once per layer, the KV used by the main attention and the search keys needed to pick positions. It is not actual memory traffic.

In V3.2, the KV read by attention is 61 layers × 2,048 positions × 1,152 B ≈ 144 MB, less than 1/60 of V2's 9.06 GB. In exchange, the indexer scans the keys of every position: 61 layers × 131,072 × 256 B ≈ 2.05 GB. Counted this way at BF16, search keys make up about 93% of the logical reads. That alone does not mean picking positions takes most of the execution time, because computation and actual memory access patterns differ.

The indexer is still cheap because each key is small (128 dimensions, FP8), every head reads the same key, and there is no softmax, only ReLU and a weighted sum. But it still scans the whole context. Cutting this cost together with storage is the task V4 takes on. How the indexer works is covered in the [sparse indexer article](/en/posts/model-advanced-sparse-indexer/).

## DeepSeek-V4-Flash

V4 **compresses the KV of several tokens into one entry**, reducing the **stored rows per token**. It mixes two schemes with different compression ratios across layers. **CSA** (Compressed Sparse Attention) compresses overlapping spans into one entry every 4 tokens and reads selectively with an indexer. **HCA** (Heavily Compressed Attention) compresses 128 non-overlapping tokens into one entry and reads every completed entry. Recent positions are kept separately without compression. Below we start with HCA, which is simpler, move on to CSA, and then work out the numbers. Figure 11 shows the effect.

This article uses V4-Flash as its reference. Of its 43 layers, the first 2 are SWA layers that see only recent positions; 21 are CSA and 20 are HCA. It is also worth noting up front that V4 is not MLA with a compressor added. V4 does not expand per-head K and V from a latent the way MLA does. **A single 512-dimensional entry serves as both Key and Value for every head.**

### HCA: 128 tokens into one

In this article, the uncompressed KV of the last 128 positions is called the **local KV (SWA)**. What is compressed and built up across a long context splits in two. The compressed KV that attention actually reads is the **main KV**, and CSA, shown later, adds search keys that pick positions to read. The main KV and search keys together are the **global KV**. Here "local" refers to the range of recent positions. The V4 report describes the branch that reads recent positions as sliding window attention; the names local KV, main KV, and global KV come from the V4.1 report.

### CSA: compress with overlap and read selectively

CSA adds two things to the same frame as HCA. Compression spans overlap, and an indexer picks which entries to read.

### Working out V4-Flash's number

CSA layers store a 512-dimensional main KV entry and a 128-dimensional search key every 4 tokens, and HCA layers store a 512-dimensional main KV entry every 128 tokens.

On structure alone, counted at the same BF16, that is 21 × 640 × 2 B ÷ 4 + 20 × 512 × 2 B ÷ 128 = 6,880 B, about one-tenth of V2. The width of the stored vector (512) is close to MLA's 576, but the stored rows per token dropped to 1/4 and 1/128.

The deployed format stores main KV entries mostly in FP8 and search keys in FP4. The format used in this article is 584 B per main KV entry and 68 B per search key.

```text
V4-Flash: 21 layers × (584 + 68) B ÷ 4 + 20 layers × 584 B ÷ 128 ≈ 3,514 B
          with page alignment padding ≈ 3,563 B  (about 1/1,104 of MHA)
```

<details>
<summary>More detail: the V4-Flash cache format</summary>

```text
Main KV entry: 448 non-RoPE dims × 1 B (FP8 E4M3) + 64 RoPE dims × 2 B (BF16)
               + one UE8M0 scale per 64 channels, 1 B × 7 + padding 1 B = 584 B
Search key:    128 dims × 0.5 B (FP4 E2M1)
               + one UE8M0 scale per 32 channels, 1 B × 4 = 68 B
Page (256 tokens): CSA KV 64 entries × 584 B = 37,376 B → aligned to 576 B units: 37,440 B
                   HCA KV 2 entries × 584 B = 1,168 B → 1,728 B
                   CSA search keys 64 entries × 68 B = 4,352 B (no padding)
Per token: (21 × (37,440 + 4,352) + 20 × 1,728) ÷ 256 ≈ 3,563 B
```

This calculation applies pages of 256 original tokens and the alignment rules. Page padding can vary with the engine's page settings.

</details>

On top of this there is a separate **local KV cache**. All 43 layers keep the KV of the last 128 positions without compression. In the deployed format that is 43 × 128 × 584 B ≈ 3.2 MB. This value stops growing once the last 128 positions are filled. But as the per-token growth shrank, local KV became a larger share of storage. Approximating global KV as per-token growth × context length, the two are about equal at roughly 900 tokens. For shorter contexts, the local KV cache is larger. The approximation ignores rounding of compressed blocks and intermediate compression state.

Reads (the right chart of Figure 11) also dropped. The KV read by attention is about 38 MB, and the keys read by the indexer about 176 MB. That is less than V3.2's 2.05 GB because search keys are compressed 4× and only 21 layers use the indexer. HCA layers read every compressed entry, so that part keeps growing in proportion to context.

## DeepSeek-V4.1-Flash

V4.1 changes compression and selection with **CSA2** and shares KV and selection lists across layers. This brings the number of layers that store global KV down to four, and storing main KV in FP4 also cuts storage. In addition, the **CED** structure, together with an approximation that recomputes only the recent span, reduces prompt-processing compute. Below we look at the changes to compression and selection, cross-layer sharing, and CED in that order, then work out the numbers. Figure 20 shows the effect.

### CSA2: compression without overlap, and the search key

CSA2 changes two things within a layer. Compression spans no longer overlap, and the search key is built from the main KV instead of by a separate compressor.

</AnnotPart>
<AnnotPart fig="csa2-flow/07-compression-span" panels="2">

### Sharing KV across layers: Full, Reindex, Reuse

Until now, every layer stored its own KV. In V4.1-Flash, **four Full layers build and store global KV**, and the remaining CSA2 layers share it. The first two layers use SWA only, and all 40 layers build their own local KV.

Each CSA2 layer is fixed to one of three modes.

<Annot fig="csa2-flow/01-three-modes" n={23} layout="cols" whole>
<AnnotPart fig="csa2-flow/01-three-modes" panels="1" xr="0-0.342">

A **Full** layer builds new main KV and search keys and picks its top-k with its own indexer. **Only Full layers store global KV.** Full is not dense attention over every position either; it reads only the top-k.

</AnnotPart>
<AnnotPart fig="csa2-flow/01-three-modes" panels="1" xr="0.342-0.675">

A **Reindex** layer borrows the main KV and search keys of the most recent preceding Full layer and picks positions again with its own indexer query.

</AnnotPart>
<AnnotPart fig="csa2-flow/01-three-modes" panels="1" xr="0.675-0.981">

A **Reuse** layer has no indexer. It borrows both the main KV and the selection list from earlier layers.

</AnnotPart>
<span slot="caption">Figure 23. The three modes of a CSA2 layer: what it builds and what it borrows.</span>
</Annot>

In all three modes, the Query and local KV are built in the layer itself, and each layer computes its own attention. What is shared is the global KV and the selection list, not the result of attention. The principle of cross-layer sharing is covered in the [cross-layer KV sharing article](/en/posts/model-advanced-cross-layer-kv/).

V4.1-Flash's 40 layers split into the first 20 (encoder) and the last 20 (decoder).

### CED: the decoder's global KV comes from the encoder

V4.1's encoder and decoder are not the encoder and decoder of a translation model. Both process the same token sequence causally. In decode, the current token passes through the 20 encoder layers and then the 20 decoder layers in turn. This structure is called **CED** (Causal Encoder-Decoder). The difference lies in where the KV that decoder layers read is built.

<Annot fig="deepseek-kv-cache/06-ced-sources" n={26} layout="stack">
<AnnotPart fig="deepseek-kv-cache/06-ced-sources" panels="1" xr="0-0.988">

**Left: the layer stack.** Token t passes through the layers from bottom to top. The decoder's global KV (main KV and search keys) is built not from the decoder's own hidden states but from the **encoder's final output**. The first decoder Full layer projects this output to build it, and the other decoder layers share it.

**Right: inside one decoder layer.** This layer builds the **main Query and local KV** from its own input. It then concatenates the main KV at positions picked with the search keys and its own local KV, scores them **with its own main Query**, and takes the weighted sum.

</AnnotPart>
<span slot="caption">Figure 26. A decoder layer reads KV from two sources with its own Query. Follows the CED execution described in the report.</span>
</Annot>

Even when several layers share the global KV, the Query that reads it differs from layer to layer.

This split makes it possible to cut compute in prefill, where the prompt is processed.

<Annot fig="deepseek-kv-cache/07-ced-prefill" n={27} layout="stack">
<AnnotPart fig="deepseek-kv-cache/07-ced-prefill" panels="1" xr="0-0.993">

**Encoder layers** run over every position of the prompt. Their output builds the global KV that the decoder reads, for every position.

The only cache left to prepare by running the decoder is each decoder layer's **local KV**, and local KV needs only the last 128 positions. So **decoder layers run only over the positions in the recent window.** This is called **replay**.

</AnnotPart>
<span slot="caption">Figure 27. CED prefill. Follows the bounded replay execution described in the report.</span>
</Annot>

Replay does more than project KV. It passes the recent positions through the decoder layers in order, running attention and the FFN as well. The first decoder layer takes the encoder output at those positions, each later layer takes the output of the decoder layer just below it, and during the run each layer also reads its selected entries from the global KV.

For long prompts, the number of (position, layer) evaluations in prefill is roughly halved, since the 20 decoder layers run only over the recent span rather than the whole prompt. This cuts **prefill compute**, not the KV cache, and it is a ratio of evaluations, not of time. Replay is also an approximation. Computing the hidden state at the first position of the recent span exactly would need local KV from positions before it, and replay cuts off that reference. The savings apply only to prefill. In decode, which generates new tokens, all 40 encoder and decoder layers run. CED is covered in more detail in the [CED article](/en/posts/model-advanced-ced/).

### Working out V4.1-Flash's number

Four layers store global KV. The 3 encoder Full layers store one entry every 2 tokens, and the 1 decoder Full layer stores one entry per token. One entry is 512 dimensions of main KV plus 128 of search key.

On structure alone, counted at the same BF16, that is (3 ÷ 2 + 1) × (512 + 128) × 2 B = 3,200 B, about half of V4-Flash. The compression ratio actually went down (4 → 2 and 1), but the number of layers storing global KV fell from 41 (21 CSA + 20 HCA) to 4.

The deployed format stores main KV entries in FP4: 512 dimensions × 0.5 B = 256 B, plus one FP8 (E4M3) scale of 1 B per 16 channels, 32 B, for 288 B. The RoPE part is quantized as well. Search keys are 68 B, the same as V4.

```text
V4.1-Flash: (3 ÷ 2 + 1) × (288 + 68) B = 2.5 × 356 = 890 B  (about 1/4,418 of MHA)
```

All 40 layers keep local KV for the last 128 positions. In the deployed format (FP8 with one UE8M0 scale per 32 channels, 528 B per token), that is 40 × 128 × 528 B ≈ 2.7 MB. Using the same approximation against 890 B per token, the two are about equal at roughly 3,038 tokens. For shorter contexts, keeping recent positions is actually the main storage cost.

For reads (the right chart of Figure 20), the KV read by attention is about 25 MB and the keys read by the indexer about 101 MB. Sharing KV does not stop each layer from computing attention, so each of the 38 CSA2 layers reads 512 entries. Storage is one copy, but reads happen in every layer.

## What was cut and what remains

Putting the five models together again, each generation cut a different factor.

| Model | What changed | Factor reduced | KV per token (deployed format) |
| --- | --- | --- | --- |
| Hypothetical MHA | baseline | N/A (baseline) | 3,932,160 B (BF16 assumed) |
| V2 | MLA | width of the stored vector | 69,120 B (BF16) |
| V3.2 | DSA, FP8 KV | positions read (storage grows structurally) | 48,068 B |
| V4-Flash | CSA and HCA, shared K = V | stored rows per token | 3,563 B |
| V4.1-Flash | CSA2, FP4 KV (CED cuts prefill compute) | layers that store global KV | 890 B |

Precision also went down from generation to generation. Going from BF16 to FP8 and then FP4 roughly halved storage, and then halved it again, even for the same structure.

The costs that remain are also clear. First, the **local KV cache** stays at a fixed size once the last 128 positions are filled, and its share grows as the per-token growth shrinks. Second, there is the **cost of picking positions**. In the right chart of Figure 1, most of what the sparse models read is search keys. Third, compression, selection, and CED's replay involve **approximation**. The models are trained with these structures, so equal quality cannot be assumed; quality has to be judged from the evaluations in the reports.

Finally, storage falling to 1/4,400 does not make decode 4,400 times faster. Real speed depends on compute, kernel implementation, memory layout, and batch size.
